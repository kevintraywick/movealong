### The mail strip (2026-09-23)
- **Up to five unread Gmail threads stacked on the tip bar**, each row the tip bar's height (`#mailStrip`, fixed, `bottom` set from the tip bar's measured height; `body` padding grows with it). A **gap one tip bar tall** (Kevin: the strip's bottom rule and the bar's top rule read as a double line at 8px) sets it apart. Columns: sender · light · action chip · **subject capped at 20 chars** (full subject in the tip when cut) · body (grey; **100 chars, but 40 for archive/delete/junk rows**, so the long lines are the ones worth reading) · age; the last row's age slot becomes **`+N`** (links to Gmail's unread search) when more are unread. **Nothing is bold** (Kevin). Hover a row → its `reason` in the tip bar.
- **No dot since 2026-09-26 (Kevin: "drop the traffic signals").** The grey/blue `.mail-light` column and its Option+Click flip are gone; "needs you" still sorts a row first and tints its action chip blue. `attention` and `inbox_senders` stay in the data (Tom still sets it; nothing on the board changes it now).
- **Tom reads mail in context (2026-09-24, after City Eyeworks came up grey the day of the appointment).** The recipe's step 3 has him read, once per run, the next 14 days of calendar (the heartbeat now does **calendar first, then mail**), `get_brief`, `list_tasks`, and `in:sent newer_than:60d` for who Kevin corresponds with, and open a thread only when the preview can't tell. Reasons name the context that decided them. Kevin's direction: "give Tom more conversational awareness" across mail and calendar.
- **Reply drafts and people notes (Kevin's Q1/Q2 yes, 2026-09-24).** A `reply` row now gets a **real Gmail draft**, threaded (`create_draft` with `replyToMessageId`), and the chip opens the draft's `viewUrl`; `list_drafts` once per run means a thread never gets a second draft; mailto is the fallback. **Never sent.** The heartbeat's allow-list gained `list_drafts` and `create_draft`. **`note_from_mail`** (MCP → `POST .../users/:slug/brief/mail-notes`) records who a person or organization is to Kevin — "City Eyeworks is my eye clinic" — into **`users.brief_mail`**, its own columns (`LEARNED_SCOPES.mail`) because the task monitor rewrites `brief_learned` wholesale. On the brief page they sit in the personal learned list tagged **from mail**; keep pins into About you, ✕ bans. The drafter reads them as `(from mail, inferred)`.
- **Option+Click on the dot was a standing choice about the sender (the dot is gone; the stored choices still apply)**, stored in `inbox_senders` (user, lowercased address, name, attention, set_at) as well as on the row — the row can be deleted as read-elsewhere before it's ever handled. `learned[].attention` (true/false/null) carries it; the recipe applies it first, matching by address or by `sender_name` for the same organization writing from another address.
- **Gestures:** click the row → the thread in Gmail. Click the chip → the action: `open`/`forward` open Gmail, `reply` follows the `mailto:` draft, `unsubscribe` opens the unsubscribe link, `task` makes **"Email: <subject> — <sender>"** on today with the email as its background; **everything is then queued and the row leaves** — no confirm (Q4). **Option+Click the chip cycles the action: Tom's suggestion → Open → the rest** (Kevin, 2026-09-26: Open is the next item). Both are recorded as corrections (`overridden_*`).
- **Architecture B:** the board never touches Gmail. Kevin's Claude runs `inbox_recipe` (MCP prompt `mail-strip`): drain `queued` in Gmail → `finish_inbox_action`, search **`is:unread in:inbox`** (Kevin, 2026-09-23: "just show the unread ones" — "unread anywhere" was tried first and filled the strip with ~200 filtered newsletters; an empty inbox means an empty, hidden strip), post ≤ 20 with `post_inbox` so freed slots refill. A failure puts the row back with its error.
- **Accept all (2026-09-24):** `#mailAll` sits **in the gap between the strip and the tip bar**, left-aligned under the action column (178px since the dot went), so it costs no row. A **grey 11px text link, not a button** (Kevin: "much more subtle" — the filled blue pill shipped first): "accept 3 · 2 to open yourself" (or "accept all 5"), blue and underlined only on hover. - **Tom learns per sender** (`inboxLearned()`): the run of identical final actions at the head of a sender's handled rows. **2 → `suggest`**; **3, with the last three taken as suggested (no correction), and the action archive/delete/junk → `auto`** — Claude does it on sight and posts the row `auto: true` (logged, never shown, never feeds the streak). - **Tom's heartbeat (2026-09-24): built, installed by Kevin.** `scripts/tom/heartbeat.sh` runs `claude -p` headless on **Sonnet** every 30 minutes (launchd agent `com.moveit.heartbeat`, `scripts/tom/install-heartbeat.sh [--uninstall]`), **quiet 11pm–6am**, one run at a time (lock dir, stale after 25 min). The prompt is one line — call `heartbeat_recipe` — so **what Tom does lives in `HEARTBEAT_RECIPE` in `mcp/tools.js`** (mail strip recipe + calendar recipe + unattended rules: never ask, never send/reply/forward, never touch events, report a blocked action `ok: false` and move on). **Tools are an allow-list**: `mcp__movealong`, Gmail search/get/trash/unlabel/spam, Calendar list — anything else is refused because a headless run has no one to ask. **It runs from an empty folder** (`~/Library/Application Support/MoveIt/heartbeat`), not the repo: in the repo every tick would load this CLAUDE.md and the project settings file (whose allow-rule warnings flooded the log). Logs: `~/Library/Logs/moveit-heartbeat.log` (one line per run), `.stderr.log`. It reads the local `server/mcp` code, so recipe edits take effect on the next tick without a deploy. **The calendar recipe pins the query window to exact dates** — the first headless run dropped Oct 6 flights as "outside the window" when it was inside; the model is told to send everything and let the board drop what's out. **Installing it was left to Kevin**: the auto-mode classifier blocked a third manual run, and an unattended job that trashes mail is his call. **The symptom is an empty strip**: clicking every row queues them all and nothing refills it (2026-09-24, Kevin: "my emails are not showing up"). Also: **the Claude Code auto-mode classifier blocks some Gmail writes** (trash, unlabel) as external-system writes — a blocked action is reported `ok: false` so the row comes back, never retried around the block. The board re-reads every 2 minutes while visible. **Reloading the board asks Tom to check the mail (2026-09-26).** The page POSTs `.../inbox/check` once per load, stamping `users.mail_check_wanted_at` (skipped when mail was posted in the last 5 minutes — `MAIL_CHECK_FRESH_MS`); the request is answered by the next `post_inbox`, so nothing clears it. **The launchd agent now ticks every minute** and `heartbeat.sh` decides: a full run when 29+ minutes have passed (`.last-full` stamp in the work folder, quiet hours respected), otherwise one GET of the check (board address and key read from the `movealong` MCP registration in `~/.claude.json`) and, if wanted, a **mail-only run** — `heartbeat_recipe` with `part: "mail"` → `MAIL_CHECK_RECIPE` — **at most every 5 minutes** (`.last-mail`, stamped before the run so a failure isn't retried each minute). Reloads in quiet hours still count. Mail lands 1–3 minutes after a reload, and only while the Mac is awake; the page re-reads the check every 20s for 6 minutes and refreshes the strip when it's answered. **Changing the interval needs `install-heartbeat.sh` re-run.**

### When the strip goes quiet: check that launchd is still ticking (2026-09-30)
- **Symptom:** no mail on the board, and `~/Library/Logs/moveit-heartbeat.log` has no `start` lines for hours outside quiet hours. **Check:** `launchctl print gui/$(id -u)/com.moveit.heartbeat | grep runs` twice, a couple of minutes apart. If the count doesn't move, launchd has stopped starting the job; the script isn't the problem.
- **Cause, 2026-09-29:** with `StartInterval` 60, the job sat `pended nondemand spawn = interval` after the Mac slept and never ran again. **Reinstalling did not clear it.** The agent now uses an empty **`StartCalendarInterval`** (every minute by the wall clock), which ticked at once. `launchctl kickstart gui/$(id -u)/com.moveit.heartbeat` forces a single run.

## Open in Apple Mail, accept-all takes Open rows, Reply opens the Gmail draft (2026-10-01)

- **Open uses Apple Mail** (Kevin's Gmail is set up in Mail): `message://%3C<Message-ID>%3E`. The Gmail connector never exposes the Message-ID header (no headers in any `get_thread` format, `RAW` unsupported), so **`scripts/tom/mail-ids.mjs` fills it in from the Mac** after every heartbeat pass. It reads Mail's `~/Library/Mail/V*/MailData/Envelope Index` (sqlite3, `immutable=1`), matches by sender address plus `date_received` within 15 minutes of Tom's `received_at`, reads the `.emlx` (`Data/<thousands digits reversed>/Messages/<rowid>[.partial].emlx`), and `PUT /api/inbox-items/:id {message_id}`. Rows without one, and phones and iPads (`message://` is Mac-only), keep the Gmail `view_url`.
- **Accept all now includes Open rows.** It opens them first, while the click still counts as a user gesture: one row goes to Mail; several go to **one Gmail search tab** (`rfc822msgid:… OR (from:… subject:"…")`). In Gmail search, `{}` means OR, so AND groups use `()`. Reply, forward and unsubscribe each need their own page, so they stay for a click of their own.
- **Bug fixed:** the recipe tells Tom to set `reply_link` to the Gmail draft's viewUrl, but the server only accepted `mailto:`, so the draft link was silently dropped and Reply opened the thread instead. `reply_link` now takes `https:` or `mailto:`.
- **Under launchd, macOS privacy blocks `~/Library/Mail` (EPERM) until the node binary has Full Disk Access.** That's confirmed: it works from a terminal and fails from the heartbeat. The script then logs `mail-ids: macOS blocks reading Apple Mail — give <path> Full Disk Access` and Open falls back to Gmail. The path is the real binary (`/usr/local/Cellar/node/<version>/bin/node`), not the `/usr/local/bin/node` symlink, so **a Homebrew node upgrade drops the grant**. Re-add it then. To test the launchd context without waiting for a tick: `launchctl submit -l <label> -- /bin/bash -c "export PATH=…; node scripts/tom/mail-ids.mjs > out 2>&1"`, then `launchctl remove <label>`.
