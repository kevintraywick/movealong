# The brief and the feedback loop

> Read when touching /brief, briefFor(), learned lists, step_events, how-you-work lines or holdout drafts. Moved out of CLAUDE.md verbatim on 2026-09-30; keep adding here, not there.

### The brief (/brief/:projectId, 2026-09-02)
- **Standing notes the assistant reads before every AI call.** **Two layers merged at call time**: `users.brief` (personal, every board) then `projects.brief` (this board). `briefFor(ownerId, projectId)` in `server.js` merges and feeds phase 1 (`generateSubtasks`), cost triage, whole-task research and single-step research. Not mocks; ↺ gets it via generate.
- **Freeform, one note per line, bullets optional.** Rules, preferences and facts all reach the model as context; classifying each line is the decision the app exists to delete. Server strips a leading `- * •`. No length cap (a cap would inhibit "learning" him); containment comes from the next two points.
- **Triage filters, research sees only what fits.** `triageCosts()` takes the brief and returns `{costs, brief}` — indexes of notes that bear on this task. `runResearch()` passes only those lines. If triage fails, research sees everything. Phase 1 and single-step research get the whole brief.
- **Every call reports back** — with a brief present, the prompt asks for `{"steps": [...], "brief_used": [indexes], "question": "..." | null}`; `unwrap()` in `ai.js` accepts either shape. `takeBriefReport()` mirrors `takeUsage()`. `applyBriefReport()` in `server.js` upserts `brief_usage` (keyed by **line text**, per scope + owner) and inserts the question into `brief_questions` — deduped case-insensitively against open questions, **capped at 7 open per board** (`BRIEF_QUESTION_CAP`).
- **The page** (`public/brief.html`, one static file like `/task`) is **two columns**: an inbox pane *"The assistant wishes it knew"* on top (blue; each question shows its task; answer goes into **About me** on Enter or **This board** on ⌘⏎, or **skip**). **Left, quick forms:** **You** (full name, goes-by, phone, email, address, Discord, notes) and **Health** (allergies, medications, conditions, doctor, pharmacy, emergency contact + phone, notes) — label-over-field, autosave on input/focusout, stored as JSON in `users.brief_contact` / `brief_medical`, each filled field becoming one `Label: value` line. **Right, open-ended:** **About you**, **Travel**, **About this board** — autosaving textareas, with *What the assistant has used* beneath (lines by use count, never-read greyed). The page reads the person from `localStorage['movealong.session']` and sends `x-ai-key`.
- **About you and About this board maintain themselves — the task monitor.** Each has a `brief_learned` list (newline text on `users` / `projects`) rendered under the textarea in **full colour, not grey** (Kevin: "they shouldn't be in gray"). `POST .../brief/learn { scope }` runs `learnBrief()` in `ai.js` (no tools, ~1k tokens) with pinned lines, current learned list, rejected list and the last 40/60 task descriptions, storing the **complete new list** (max 8). Runs **on page open** only when ≥ 3 tasks were created since `brief_learned_at` (`LEARN_MIN_NEW_TASKS`). **`keep`** (`POST .../brief/learned { scope, line, action }`) moves the line into the textarea — pinned, tagged `(personal)` instead of `(personal, inferred)`; a stated note outranks an inferred one; the monitor never restates it. **`✕` drop** appends to `brief_rejected`, never re-proposed. Both `ai.js` and the route filter the model's answer against pinned + rejected. Replaced the one-shot "Draft from my tasks" button. Billed as `kind = 'brief_learn'`. Travel is a plain pane (monitor not extended to it).
- **Door: the board popup** (click the tab you're on) → **Brief the assistant**, above Rename. Opens `/brief/:id` in a new tab.
- **Sections** are `PERSONAL_SECTIONS` in `server.js` — `contact` and `medical` (kind `fields`, with `CONTACT_FIELDS` / `MEDICAL_FIELDS`), `personal` and `travel` (kind `text`) — plus the board's `brief`. That table drives merge order, `brief_usage` scope names, GET/PUT field names and validation. Lines reach the model **tagged by section** (`briefText()`: `(travel) Home airport BNA`, `(personal, inferred) …`), and the clause in `ai.js` says contact/medical notes shape a step but are **never copied into step text** (a phone number in a subtask row would land on a shared board). The page lede says it's link-reachable with no sign-in.
- **Financial information is deliberately NOT a section** (2026-09-02): no auth, unencrypted SQLite. When agents can spend, the shape is *policy in the brief* ("up to $50 without asking") plus *money that lives elsewhere* (per-task Stripe Issuing virtual card with a cap, or a checkout approved via the review-row idiom).
- **Other people's contacts are back-burnered** (Kevin, 2026-09-02). Tool preferences (OpenShot, Resolve, Nano Banana keys) are prose only; keys belong to agent dispatch.
- **Where this is headed** (`reference/roadmap.md`): a feedback loop on any task, a history/day page that gamifies completion, richer task outputs (maps, recipe pages, images, dashboards), the board as an "Alfred" that improves over time. The brief is the memory that loop writes to.

### The feedback loop — step events and how-you-work lines (2026-09-12)
- **Direction:** `reference/feedback-loop-brainstorm.md` (three loops, blocker types, the delegation ladder, build order). Kevin's answers: **asks feed the brief** (a missing contact is asked in-line and lands in a People section — asks only, no vCard import until auth); **`mailto:` is fine as "Open it"**; **working-style lines ship inside the existing personal learned list — ask him later whether they should move to their own pane**; and **the subtask pane must not feel overwhelming when first presented** — drafts, previews and missing-info asks go in a **secondary pane beside the subtask pane, opened by hovering the step's "Draft"** (email: glance the draft, unknown recipient input highlighted, *Open in Mail* / *Send*). Holdout drafts: built (below).
- **`step_events` is the raw material** — one row per user gesture on a drafted step: `tick`, `untick`, `edit`, `adopt`, `promote`, `research`, `assign`, `regenerate` (task-level, `subtask_id NULL`), `link_click`. Logged server-side at the receiving route; `link_click` is the one beacon (`POST /api/subtasks/:id/events`, allowlisted names) via a capturing click listener on `.subtask-item a.task-link`; rows carry `data-subtask-id`. **`ms_since_generated` is load-bearing**: a tick is the delete, and only latency separates "ticked 4s after drafting" (rejected) from "ticked a day later" (done); same for ↺ at 10s vs after three ticks. `step_text` is copied in so the digest survives deletion.
- **Nothing scores the log.** `stepDigest()` renders it as a story and `learnStyle()` in `ai.js` (same contract as `learnBrief`) returns **how-you-work lines phrased as instructions to the drafter** ("never draft phone-call steps — they get ticked off untouched"), patterns seen at least twice. Stored in `users.brief_style` / `brief_style_rejected` / `brief_style_at` — own columns so a later move to their own pane is a render change. `LEARNED_SCOPES` is a per-scope column map (`personal`, `board`, `style`); `learnedRow()` reads through it. Runs on brief-page open (`learn('style')`), gated on `STYLE_MIN_NEW_EVENTS` (8).
- **On the page** style lines sit in the personal "Learned from your tasks" list with a blue **how you work** tag; rows carry `data-scope`, so **keep** pins into About you and **✕** goes to `brief_style_rejected`. The drafter sees them tagged **`(how you work, inferred)`** via `briefFor()`.
- **Holdout drafts (Kevin's Q1 yes, 2026-09-12).** `holdoutBrief()` in the generate route: when any how-you-work note exists, a task's **first** draft gets an arm — `rules` or `holdout` (notes stripped, `HOLDOUT_RATE` 0.1, user not told) — on `tasks.draft_arm`, notes in play in `tasks.draft_rules` (JSON). **A ↺ keeps the task's arm.** `ruleStats()` scores each note by **quick-reject rate** (`quickRejectRate()`: ticks and ↺ inside `QUICK_MS` 60s over steps drafted), with vs holdout since it first appeared. `retireUselessRules()` runs at the top of every style learn: after `HOLDOUT_MIN_TASKS` (6) drafts in **each** arm, a note that doesn't beat holdout by `HOLDOUT_MARGIN` (0.05) moves to `users.brief_style_retired` (never re-proposed; shown greyed with a **retired** tag) — **keep on a retired line un-retires it**. The brief GET returns `style_trial` (per-note counts and rates: "15 with · 15 without · rejects 33% vs 33%"). `HOLDOUT_RATE` reads an env override **for tests only** (the test ran at 0.5). **Two test traps:** `AI_LIMIT_PER_IP_HOUR` (20) silently sends later drafts to mocks, which never reach `holdoutBrief()` — lift it in any test drafting more than ten tasks; and the stub's `brief-seen.txt` goes stale the moment that happens. Rule *decay* is **not built** — the monitor's rewrite drops stale ones.
- **Not verified with a live model** — the stub proved the plumbing. Read the first real `learnStyle` output before trusting it.
