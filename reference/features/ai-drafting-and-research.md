# AI drafting, research, budget and cost

> Read when touching ai.js, the generate/research routes, prompts, models, rates, the 🔎 switch or step cost chips. Moved out of CLAUDE.md verbatim on 2026-09-30; keep adding here, not there.

### Subtask Quality: Actionable, Not Generic
Subtasks must be **specific, actionable, research-backed** — never PM filler.

Bad: "Define requirements and scope", "Research materials and tools needed", "Create a detailed plan".
Good: "Pick a location — sunny, 5-10 ft high, near trees (birdsonly.com/placement-guide)", "Choose target birds for your area (audubon.org/native-plants/98101)", "Decide: buy plans online ($5-15 on Etsy) vs design your own", "Get materials — cedar boards, screws, waterproof glue (Home Depot list)".

**Concise (Kevin, 2026-09-16: "way too verbose"):** the draft prompt's rule 0 caps a step at ONE action, under 12 words before any link, verb first, one link at most, no rationale clauses — the pane is 178px wide. The list prompt (12) and research pass (14) already carried caps; the ordinary draft had none.

Principles: prefix a mini-label when helpful ("Project plan:", "Decision:", "Research:"); include real, relevant links (retailer searches, guides, location-aware resources); surface the actual decisions ("Decide: cook vs cater vs potluck (Thumbtack caterers near you)"); be domain-specific (bird species and wood types, not "gather materials"); AI-assigned subtasks return concrete options, prices, links and comparisons, not summaries.

### Two-phase subtasks (draft now, research behind it)
- Adding a task runs **phase 1**: a fast reasoning-only call returning 7 steps in seconds — engage the user's brain immediately, not be right yet.
- **Research is opt-in, per step (since 2026-08-16).** `projects.research_enabled` defaults to **0**; the trigger is the **🔎 on each step's rail** (`POST /api/subtasks/:id/research`). The pane-wide "Research these steps" button is gone — researching all seven decided *for* the user which steps were worth money when only two or three are. The **🔎 Research switch in the header** (beside 🧠) makes every new task research automatically. Off by default because at ~$0.10 a researched task, auto-researching everything empties a $5 board in about a week.
- **↺ never researches**, switch or no switch (`req.body.regenerate === true`). Topping up one row costs a whole search budget (`max_uses` is per call, not per row).
- **Phase 1 drafts on Opus 5, research on Sonnet 5 (2026-09-08).** `ai.js`: `DRAFT_MODEL = 'claude-opus-5'` with `output_config: { effort: 'medium' }` and a 30s abort; `MODEL = 'claude-sonnet-5'` for whole-task and single-step research. The draft is judged on whether the first step is the right first step (judgment, ~2-3¢ a draft); research is search-bound and Sonnet + `web_search` is already the cheap configuration. **Kevin's premise was that the draft ran on Haiku; it never did** — Haiku only does cost triage. Fable 5.1 was declined for the draft (5× Opus, thinking floor, needs `refusal` handling and a 30-day retention org setting); it's a candidate for agent dispatch. `max_tokens` went 2048 → 4096 because thinking tokens count against it. **Opus latency was not measured before shipping** (no local key; `railway run` was blocked by the permission classifier) — if drafts feel slow, `DRAFT_EFFORT = 'low'` is the first knob. Add a `RATES` row whenever a model constant changes; `meterUsage(data, DRAFT_MODEL)` is passed explicitly.
- **Phase 2 (`runResearch()` in `server.js`) runs behind the HTTP response**, fire-and-forget, with the Anthropic `web_search` tool, rewriting rows **in place**. It never adds, removes or reorders steps: results match back **by index**, and every row is re-read immediately before writing so a row the user ticked or promoted mid-flight is skipped, not resurrected. Load-bearing — research takes 15-60s while the user watches the pane.
- **A step is replaced outright only at ≥ 0.8 confidence** (`RESEARCH_REPLACE_CONFIDENCE`). The model returns `refined` (always) plus `illogical`/`confidence`/`replacement`; the gate is server-side. Ordinary vagueness is refined, never replaced.
- **`subtasks.provisional` = "awaiting research"**, watched by the frontend poll; set only when phase 2 will actually run. It no longer changes how a row looks — a draft is a finished state.
- **`subtasks.researched` marks rows the pass rewrote**; they render **light blue** as a row tint (`#f0f9ff` + inset `#7dd3fc` edge) with blue-tinted text, *not* blue text alone — AI steps are full of `.task-link` anchors at `#0284c7`, and blue text around blue links is unreadable. Any "colour the text" request in the pane hits this wall.
- **The frontend polls** (`pollResearch()`, 3s, capped ~2 min) while an open pane holds a provisional row — no websockets, no queue. Close the pane and research still finishes. `repairInterruptedResearch()` clears the flag on boot (a restart mid-research would otherwise leave rows greyed forever).
- **`runResearch` must call `flushDb()` itself** — `res.on('finish', flushDb)` already fired for the request that started it (same trap as calendar sync).
- **Per-step research runs at `SINGLE_STEP_SEARCHES` (2), not the whole-task 5** — `max_uses` is per call, so one row at the batch budget costs as much as all seven. It **writes the same three-state cost fields** as `runResearch()` (without that, a row researched from its own button silently got no price) and skips cost triage (triage aims a shared budget across seven rows; nothing to aim with one).

### AI budget (per board, per month)
- `projects.ai_budget_usd` — whole dollars, **default $5** (cents-level control is exactly the decision this app saves people from).
- **On/off = the 🔎 Research switch in the header** (`#researchSwitch`, same `.assistant-switch` markup as 🧠 and 📅). State is **per board** (`projects.research_enabled`), unlike its neighbours (per browser) — it spends *this* board's money, so it repaints from `refreshBudget()`.
- **Turning it ON opens a cost dialog** (`#researchWarnModal`): ~$0.10 a task, this board's spend so far, a **Change budget** link, and **Don't warn me again** writing `localStorage['movealong.researchwarn'] = 'off'` (per browser — it records that this person has read the price). Turning it **off** never warns.
- **`#budgetBar` under the board is gone** (2026-08-14). Spend is in the switch's `title` tooltip, and **Shift+Click the switch edits the budget** (same idiom as Shift+Click 🧠 for the AI key). That's the *only* permanent path to the budget after the dialog is dismissed; the over-budget toast is the other reminder.
- **It gates research only.** Phase 1 always runs — an exhausted board still drafts steps, marks them final, and says so (`research_status = 'over_budget'`).
- Spend is metered from the API's own `usage`, **including `server_tool_use.web_search_requests` at $10/1000**, one row per call in `ai_usage` — an audit trail, not a counter. Rates live in one constants block at the top of `ai.js`; nothing reads a live price list.
- **~$0.10 per researched task** at `max_uses: 5` — about half is the searches ($0.01 each), so `max_uses` is the real cost lever. $5 ≈ 50 tasks. (Haiku cost-triage adds a fraction of a cent.) **Per-step research changed the arithmetic:** seven steps one at a time ≈ $0.21 (7 × 2 searches) vs ~$0.10 batch — cheaper per click, pricier if someone researches everything; the intended trade.
- **`ai.js` rates are hand-maintained and per-model.** Sonnet 5 is $2/$10 per MTok where Sonnet 4.6 and earlier were $3/$15. Re-check the pricing page when `MODEL` changes; cache reads bill at 0.1x base input and writes at 1.25x — folding them into base input overcharges reads 10x.
- **Mixedbread's *Toast 1* search agent was evaluated and declined (2026-08-16):** $0.016–0.023/query, ~8s median. Its "10x cheaper than a frontier model" compares against a frontier model *as the search agent*, which this app doesn't do; the saving is a few cents a task against a $5 cap for a second vendor and failure mode in the path the user watches live. **Revisit only if** research latency becomes the complaint (8s would delete `pollResearch()`) **or** step pricing pushes past `max_uses: 5`. First settle whether it searches the open web or only an indexed corpus, and whether it returns the index-matched structured objects the pass needs.
- **`AI_LIMIT_*` and this budget differ:** those are abuse brakes on a public deployment (per IP, per day); this is the owner's own cap.
- `web_search` takes `user_location`; the only location known is the IANA zone from a connected **calendar feed** — enough to localize "stores near me".
- Calendar rows carry `project_id = NULL`, so they have no board to bill and are never researched.

### What a step costs (materials, labour, services)
- **Two different costs, never one number.** `ai_usage` is metered actuals. `subtasks.cost_*` is an *estimate about the world* — uncertain, local, time-varying. Never add them together.
- **Written only by the research pass, as extra fields on each verdict** — a separate cost call would double the search budget for information the model already had.
- **A Haiku 4.5 triage call runs first** (`triageCosts()` in `ai.js`), labelling each step `material | labor | service | none`. Most are `none`; labels ride into the research prompt so searches concentrate on the rows that spend. The point is the search budget, not the token saving. Triage failure is caught and logged; research decides for itself. It gets its **own `ai_usage` row** (`kind = 'cost_triage'`).
- **Ranges only**, never point estimates; `cost_basis` ("24x 6ft cedar picket at $4.28") is **required**. `cost_source_url` and `cost_as_of` ride in the chip's tooltip — a price with no date is worse than none.
- **Three states:** a priced row; `cost_kind = 'none'` (research ran, spends nothing — an *answer*); `cost_kind = NULL` (never researched, or too shaky). The pane's total prefixes **≥** whenever any pending row is NULL.
- **The confidence gate lives in `runResearch()`** beside the 0.8 gate. `COST_MIN_CONFIDENCE` is **0.5** — lower because it only guards adding a figure the user can take or leave, and a range carries its own uncertainty. Below it the estimate is dropped.
- **Rendering:** grey chip after the step text (`.subtask-cost`), an `<a>` when a source URL exists; task total opposite the title in the pane header (`.subtask-cost-total`). Whole dollars — "$91.40–$127.75" claims false precision.
- **`ai.js` rates are a per-model `RATES` map**; `meterUsage(data, model)` takes the model explicitly.

### Assistant switch (from Key Design Decisions)
- AI agents research after initial generation so the user gets immediate feedback first
- Day capacity: max **7** pending tasks per (owner, project) per day (was 10 until 2026-09-02). **A task typed onto a full day lands there and pushes one existing task forward (2026-09-13)** — `bumpableTaskOn()` in the create route picks the **oldest never-ranked** pending task (not locked, goal, calendar, inbox or review), or the visual bottom when every row is hand-ordered, and moves it to the next day with capacity, cascading successors. (Visual bottom was rejected as default because a never-ranked task sorts there by creation time, so rapid entry would push out the task typed a moment earlier.) Response carries `bumped: {id, description, from, to}`; the frontend toasts "Made room — “…” moved to Tue". If nothing is movable it **overflows as before**. Create is the only bump site; **promote and `spawnNextRepeat` still overflow** (`findDayWithCapacity()` has exactly three callers). The help page's overflow card text is updated; **its vignette still animates the old overflow**. Assign, return, move and **lock** are uncapped — a deadline is a fact, not a request for room.
- **AI assistant master switch** (🧠, `localStorage` `movealong.assistant`, default on): on, adding a task auto-generates subtasks and opens the pane; off, the task is created bare.
  - **Shift+Click 🧠** prompts for the **AI access key** (`localStorage` `movealong.aikey`, sent as `x-ai-key`). With `AI_ACCESS_KEY` set server-side, only matching requests get real AI (`aiKeyAllows()`, timing-safe); others get mocks. Second layer: `AI_LIMIT_PER_IP_HOUR`/`AI_LIMIT_GLOBAL_DAY`.
  - **Known gap:** the toggle only gates `addTask`/`addTaskFromMaster`. The ↺ button (`regenerateSubtasks()`) calls `POST /tasks/:id/generate-subtasks` unconditionally. Fix both together.
