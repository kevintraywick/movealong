# Board row behaviour

> Read when touching a task row: lock/deadline, series, day counter, manual order, → moves, inline edit, goal, repeat, links. Moved out of CLAUDE.md verbatim on 2026-09-30; keep adding here, not there.

### Locking tasks to a date (deadlines)
- A task can be **locked** to a date (`tasks.locked`; the lock date is `scheduled_date` while locked).
- **A future lock date is a pending deadline, not a move (2026-09-06).** Picking a future day in the 📅 popup writes `tasks.due_date` and leaves the task spilling forward; the tasks route turns it into a real lock **when that day arrives** (`locked = 1, scheduled_date = due_date, due_date = NULL`, run before spillover). If the board wasn't opened that day, it lands on the now-past due date and anchors the board back. A due date on or before today is just a lock. Pending state: faded 🔒 (`.task-lock.due`; the dashed amber edge was dropped 2026-09-15); the popup reads "Locks to ⟨date⟩ when that day comes" and offers **Cancel the deadline**. Any real lock/unlock settles a pending due date; assign and return clear it. Refused on calendar rows.
- **Gestures:** Shift+Option+Click the task body quick-locks to its current day (with confirm); the 📅 icon opens a popup to lock-to-this-day, pick a future date, or unlock. Locked shows 🔒. **No left edges since 2026-09-15** — the amber `.locked`/`.due` and grey `.calendar` `border-left` rules are gone (Kevin: "drop the vertical lines"); the icons carry the state.
- Locked tasks are **exempt from spillover**. A past-due locked task **pulls the calendar's first visible day back to its lock date** (anchor = min(today, earliest locked-incomplete date)); "today" stays highlighted by real date.
- **Today's card has a 2px white border (2026-09-10)** (`.day-card.today`), kept through `.selected` and `:hover` with an explicit `body.dark` override (the base dark card rule out-specifies it). Nearly invisible in light (white card on `#f8fafc`), a lit frame in dark. Kevin asked for white specifically.
- **Overdue day panes get a red border.** When the anchor is pulled back, every day before today (`isOverdue: key < todayKey` in `generateDays()`, `.day-card.overdue`) shows 2px `#ef4444` border + red header/date. Gotcha: `selectedDayIndex` defaults to `0`, so the anchor-back day is auto-selected — `.day-card.overdue.selected` must out-specify `.selected`'s blue border while keeping the shadow.
- Moving a locked task forward asks for confirmation; the lock follows. Assign/return clear the lock.
- **A locked task sorts to the top of its day (2026-09-02).** `sortByPosition()`: calendar events → locked → everything else. Display only — `position` still written, so unlocking drops it back. Calendar events outrank the deadline (a judgment call).
- **A locked task on its lock day renders red text** (`.task-item.locked-today`, gated on `!completed && scheduled_date === todayKey`), overriding everything including series color/tint.
- **Project tabs never move.** All boards render into one `#projectTabs` flex row in the user's order; the active one is styled in place (`.active`: tinted background + blue border in light, **white border** in dark via `body.dark .project-tab.active`). The old two-container split made the selected board jump to the front. Every tab shares one geometry (3px/10px, 12px), `.due` compensates its 2px border with 2px/9px padding, and **`.active` carries no `font-weight`** (bolding widens the tab and nudges the row).
- **Renaming a board** lives in the board popup: **Rename this board** (third row, after Preferences and Brief the assistant), an inline field in place (`.rename-input`; Enter commits, Escape cancels). `PUT /api/companies/:sub/users/:slug/projects/:id` takes `{ name }` and **regenerates the slug** (`projectSlugFrom()`, shared with create) — nothing addresses a project by slug (the unused `/projects/:projectSlug/members` route is a collaboration leftover). The route **must stay declared after `PUT .../projects/order`** (Express matches in order; `:projectId` above it swallows `order`), and `renameProject()` mutates the existing `projects` entry in place (`currentProject` is a reference into that array). Rename is **company-wide**.
- **Deleting a board is per-user.** Clicking the active tab opens the board popup (reuses `.team-popup`/`.lock-popup-menu`, same element as the account popup) with **Delete this board**. `DELETE /api/companies/:sub/users/:slug/projects/:id` drops the caller's `project_members` row and **their own** tasks (+subtasks); the `projects` row dies only when the last member leaves. `tasks.project_id` is `ON DELETE SET NULL`, so tasks **must** be deleted explicitly or they orphan unreachably. Refuses to remove a user's **last** board (409). No undo.
- **Tab order is per-user and drag-sortable.** `project_members.position` (NULL = never dragged) orders `GET /projects` via `ORDER BY CASE WHEN pm.position IS NULL THEN 1 ELSE 0 END, pm.position, p.created_at`. `PUT /api/companies/:sub/users/:slug/projects/order` takes `{ project_ids }`, keeps only ids the user belongs to, dedupes, appends any missing. Frontend: `attachProjectTabDrag()` + `reorderProjects()` splice locally, repaint, PUT.
  - Tab drag and series drag share `dragstart`/`drop`; each gates on its own var (`draggedProjectId` / `draggedTaskId`). `justDraggedProject` (cleared on a 0ms timeout in `dragend`) swallows the click after a drop on the origin tab. Desktop only (no iOS HTML5 DnD).
- **Off-screen boards with a deadline flag their tab red.** `GET /projects` returns `due_today` per project (`locked = 1 AND completed = 0 AND scheduled_date <= today`). `renderProjectBar()` puts `.project-tab.other.due` (2px `#ef4444`, padding 2px/9px) on non-active tabs with `due_today > 0`. Refreshed from `loadTasks()` via `refreshProjectDueFlags()`, which merges into the existing `projects` array (never replaces it — that drops `currentProject`).
- **On the List view a locked task's date renders red** (`.project-task-date.locked-date`, bold). The master route SELECT is a hand-listed column list, not `t.*`, so new task flags the List view needs must be added there explicitly.

### Series (task chains / dependencies)
- **User-facing copy says "next step in a series" — never parent/child** (rewritten 2026-08-05). `parent_task_id` is internal.
- **Drag a task onto another task** to make it the next step: splices in after the target and moves to target's day + 1 (`origin_date` untouched). `tasks.parent_task_id` points at the predecessor; single successor enforced at link time (linear list). `POST /api/tasks/:id/link`.
- **Countdown circles:** members show position-from-end inside the completion circle — first step shows series size, last shows 1. Empty circle = free-standing. Day board only. Chosen after 9 mockups (`archive/pm-v*.html`).
- **Hover threads:** hovering a member lights the family (background tint), fades the board (`.board-container.threading`), and draws SVG bezier threads (`#chainOverlay`) between consecutive members. Hover-only. Colors from `CHAIN_COLORS` (violet/orange/fuchsia/indigo/cyan — no red, no green) keyed by root id; **only on hover**, resting board monochrome.
- **Move cascade:** changing a member's date (→, lock popup, any `PUT` with `scheduled_date`) shifts every later step by the same delta. **Stops at the first locked step** and **skips completed steps** without stopping. Earlier steps never move.
- **Spillover cascades too:** an overdue member spills to today and drags successors forward by the same delta (same lock-stop rule).
- **Boot chain repair:** `repairCompletedChainLinks()` splices any completed task still holding chain links (re-fetches each row before splicing). Idempotent.
- **Series never break:** assigning, deleting, or **completing** a member splices it out (`spliceOutOfChain()`). Completing severs one-way (reopening doesn't restore). Re-dropping a chained task repositions it. Frontend: `toggleComplete()` must `loadTasks()` when completing a chained task because the splice rewrites *other* rows. Consequence: countdowns renumber on completion, and a 2-step chain dissolves when either member completes.
- **Unlink:** hovering a chained pending task (day board) reveals ✂️ when it has a predecessor — the chain ROOT never shows scissors (no parent edge); cut a 2-chain from its child. Recurring support question, not a bug. Clicking (with confirm) cuts one edge — `POST /api/tasks/:id/unlink` nulls `parent_task_id`, leaving successors attached (the task becomes a new root). Distinct from `spliceOutOfChain()`.
- Frontend: `computeChains()` builds `chainInfo` (task id → chainId/countdown/color) on every `renderBoard()`. After any date change, `loadTasks()` refetches because cascades change other rows.

### Day counter (days pushed forward)
- Each task stores `origin_date` — the day first **requested** (capacity overflow counts as a push). It **never changes**: spillover, → moves, assign, return all preserve it. Any new code writing `scheduled_date` must leave it alone.
- The day board shows a light-grey **inclusive** count after the task text: days from origin to `max(scheduled_date, today)` + 1, hidden when it would read 1. So **the counter never displays "1"** — first visible value is 2 (the help page's postpone vignette shows "2" for this reason). `renderDayCounter()` in `index.html`; **day board only**. **Counts over 10 render red** (`.task-day-counter.lagging`).
- Overdue **locked** tasks keep counting. **Completed** tasks freeze at completion day.
- Pre-migration tasks backfill `origin_date = scheduled_date` on boot.

### Manual order (drag, or hover + 1-9)
Replaced the 1/2/3 priority marks on 2026-08-14. A task's rank is where it sits.
- **Drag a task to a row's top or bottom edge** to reorder within its day — a blue line (`.task-item.insert-above/.insert-below`) shows the landing. **Or hover a pending task and press `1`-`9`** for that slot; `0` sends it to the bottom.
- Backed by `tasks.position`, dense 0..n-1 within a day. **NULL = never positioned, sorts LAST** — which lets a new task append without any INSERT site knowing the column. Don't assign positions on insert; several INSERT paths (create, assign, return, `spawnNextRepeat`, calendar sync) would have to be kept in step.
  - **The one exception is promote** (`placeTaskAfter()` in `server.js`), which reuses the `PUT .../tasks/order` ordering query; any future "insert here" should call it.
- **One gesture, two meanings, split by pointer position** (`dropZone()`): middle **40%** = series link, top and bottom **30%** = reorder. Reordering is **same-day only**; across day cards the whole row means "series".
- **`dragstart` must set `effectAllowed = 'all'`.** `'link'` silently suppresses every reorder drop. `dropEffect` is set per zone (`link` vs `move`), which also makes the cursor announce the drop.
- Both gestures write through **`PUT .../tasks/order`**. Frontend splices locally, repaints, then PUTs; writes chained per `date|project` (`orderWrites`).
- **The list re-sorts immediately.** The old deferred `mouseleave` sort (`pendingPriorityRow`) is gone; a number press **holds** its task under the keyboard (`stickyTaskId`) until a real `mousemove`, so "3 then 5" still targets the moved task (re-rendering fires `mouseover` but never `mousemove`).
- **The keydown branch must stay above the `viewMode !== 'calendar'` guard** (works on Main) **and above the type-to-focus fallback** (which would swallow the digit into the add-task input). Early-returns when focus is in `INPUT`/`TEXTAREA`/`SELECT`/contentEditable.
- Hover detection reads `document.querySelector('.task-item:hover, .project-task-item:hover')`.
- **Eligible rows:** pending only. Completed, `.forwarded`, placeholder and calendar rows excluded.
- Display only — never writes `scheduled_date`, so no cascade, no spillover change, no capacity effect.
- **Migration:** the boot adding the column backfilled `position` from the old priority order (`priority DESC, created_at`) per (owner, project, day). One-shot — `ensureColumn()` returns whether it added the column. `tasks.priority` stays, unread; `PUT /api/tasks/:id` still accepts it.

### Moving a task forward (the → arrow)
- Click → for **+1 day**, Shift+Click for **+1 week**, or **hover the arrow and press `1`-`9`** to jump that many days. All paths go through **`moveTaskForwardDays(taskId, n, label)`** so the lock confirm and "series follows" notice can't drift.
- **The arrow is inside the row, so hovering it matches both hit-tests.** `hoveredForwardArrow()` is checked **before** `hoveredTaskRow()` in the digit branch. Over the row a digit is a slot; over the arrow it's days.
- **`0` over the arrow is swallowed**, not passed through.
- **`stickyArrowTaskId` holds the arrow under the keyboard** like `stickyTaskId` — a move slides the arrow to another card. One `mousemove` listener clears both. `3` then `2` is +5.
- **The move optimistically writes `task.scheduled_date` locally before the PUT.** `moveTaskToDate()` is async and nothing else updates the row until `loadTasks()` returns, so a fast second digit would otherwise compute from the stale date.

### Edit text in place (Shift+Click, 2026-09-16)
- **Shift+Click (or Shift+Right-click) a task on the board or List view, or a step / list item in a pane, to edit its text where it sits.** Shift+Click was added the same day — Kevin's right button is taken by something else on his setup. One resolver, `tryInlineEdit(e)`, behind a `contextmenu` listener and a **capture-phase** `click` listener (it must beat the row's own click, which toggles the pane); Shift with Option/Cmd/Ctrl is left alone (quick-lock, the browser). A capture-phase `mousedown` stops the list box's input taking focus first. `startInlineEdit()`: the element's text becomes an `.inline-edit` field (board-rename idiom); Enter or blur saves, Escape or empty cancels, then `renderView()`. Shift is what leaves the browser's own menu on a plain right-click. Plain click on a task still toggles the pane; Option+Click (page) and Shift+Option+Click (quick-lock) are unchanged.
- **The pink list box edits too** (Shift+Click anywhere on it → the list's name, e.g. "list things to take to Seattle"); the handler swaps the whole `.list-box` for the field.
- **`PUT /api/tasks/:id` now takes `description`** (non-empty string, trimmed, 500 cap; **400 on calendar rows** — the next sync would overwrite the title). Subtasks already accepted it (`PUT /api/subtasks/:id`, which logs a `step_events` `edit`). Inbox, review, completed and placeholder rows are left alone (no `data-task-id` on their description, or checked in the handler). List-pane rows now carry `data-subtask-id` on the row so the editor can find them.
- The row's `draggable` is switched off while the field is open — Safari otherwise starts a drag when you select text. Re-render restores it. Idle tip added.

### Goal for the day (hover + `g`, 2026-09-08)
- **Hover a pending task and press `g`** to make it today's goal; `g` again clears. `tasks.goal` (0/1). Text renders **orange** (`#ea580c`, `#fb923c` dark) and bold, day board and List; `.locked-today` is declared after it (light and dark) so a goal that is also today's deadline reads red.
- **Sorts to the top of its day under any locked task** (`sortByPosition()`: calendar → locked → goal → manual). Display only. Kevin's brief: "highest priority, which is one".
- **Persists until cleared or completed**, across spillover. Cleared by assign and return alongside `locked`/`repeat_rule`; refused on calendar rows.
- `setGoal()` re-renders at once and sets `stickyTaskId`. The keydown branch sits beside `r` with the same editing guard. Every hand-listed task SELECT carries `t.goal` (six sites) — same trap as `t.locked`.

### Repeating tasks (hover + `r`)
- **Hover a pending task and press `r`** to cycle `off → daily → weekly → monthly → off`. `tasks.repeat_rule` (NULL / `'daily'` / `'weekly'` / `'monthly'`, validated against `REPEAT_RULES`). Glyph `↻d` / `↻w` / `↻m`. **No popup** — a cadence picker is the rabbit hole; sub-daily, arbitrary intervals, weekday-only and "on the 1st" are out of scope precisely because they force a dialog.
- **Only ONE instance exists; completing it creates the next** (`spawnNextRepeat()` in `server.js`, from `PUT /api/tasks/:id` after `spliceOutOfChain`). No scheduler; nothing materialized ahead. Miss one and the single instance spills forward.
- Next date is measured from **the completed instance's own `scheduled_date`, not today**. `addMonths()` clamps end-of-month (Jan 31 + 1 month = **Feb 28**; `setUTCMonth` alone overflows).
- The new instance inherits `description`, `project_id`, `locked`, `priority` and the rule, goes through `findDayWithCapacity()`, carries **no `parent_task_id`**, and gets its own `origin_date`.
- **Locked + repeating is the intended bill combination**: the next instance inherits `locked = 1`.
- **The repeat glyph replaces the day counter** (`renderDayCounter()` early-returns on `repeat_rule`); `paintDayCounter()` removes it live on `r`.
- **Refused on calendar rows** (same guard shape as `locked`). **Cleared by assign and return.**
- Frontend: `setRepeat()` shares the `priorityWrites` chain with `setPriority()` (one chain per id). The `r` branch sits beside the priority branch — above the `viewMode !== 'calendar'` guard and the type-to-focus fallback, with the same input guard. `hoveredPriorityRow()` was renamed **`hoveredTaskRow()`**. `toggleComplete()` must `loadTasks()` when completing a repeating task (the next instance is created server-side).
- No deferred re-sort — the glyph paints in place.

### Hyperlink tasks
- Any URL in a task's text renders as `.task-link`, **opens in a new tab** (`target="_blank" rel="noopener noreferrer"`). Day board, Main page, and subtask rows; forwarded/placeholder rows stay plain.
- `linkifyText()` escapes the whole description first, then wraps `TASK_URL_RE` matches (`http(s)://…` and `www.…` **only** — so `javascript:` can never become an href). Trailing `. , ) ] ' "` trimmed. `www.` gets `https://`.
- Descriptions are **HTML-escaped now** (they used to inject raw — an XSS hole).
- Links carry `draggable="false"` so dragging from a link starts the series drag.
- Both description click handlers early-return on `e.target.closest('a.task-link')`.
- **URLs in subtask rows render as a link glyph, not text** (`linkifySubtask()`; board rows keep `linkifyText()`). The glyph sits **where the URL was**; hover shows the **domain**. Wrapping parens are eaten with the URL, surrounding whitespace is not.
  - **`SUBTASK_URL_RE` matches bare domains, which `TASK_URL_RE` never did** — the model writes `homedepot.com/s/cedar`, so AI links cost URL width *without being clickable*. Bare form is admitted only against `SUBTASK_TLDS` (keeps `$4.28` and `1.5in` out); href always rebuilt with `https://`.
- **Completing any task closes its subtask pane** (`toggleComplete()` drops it from `expandedTaskIds` on `willComplete`). The URL gate and `taskHasLink()` were removed 2026-08-05.

### Day capacity and the bump (from Key Design Decisions)
- Day capacity: max **7** pending tasks per (owner, project) per day (was 10 until 2026-09-02). **A task typed onto a full day lands there and pushes one existing task forward (2026-09-13)** — `bumpableTaskOn()` in the create route picks the **oldest never-ranked** pending task (not locked, goal, calendar, inbox or review), or the visual bottom when every row is hand-ordered, and moves it to the next day with capacity, cascading successors. (Visual bottom was rejected as default because a never-ranked task sorts there by creation time, so rapid entry would push out the task typed a moment earlier.) Response carries `bumped: {id, description, from, to}`; the frontend toasts "Made room — “…” moved to Tue". If nothing is movable it **overflows as before**. Create is the only bump site; **promote and `spawnNextRepeat` still overflow** (`findDayWithCapacity()` has exactly three callers). The help page's overflow card text is updated; **its vignette still animates the old overflow**. Assign, return, move and **lock** are uncapped — a deadline is a fact, not a request for room.

### Today and time zones (from Key Design Decisions)
- **Day keys are UTC-anchored labels, but *which* label is today is a local question.** `YYYY-MM-DD` keys and their arithmetic (`addDays`, `addMonths`, `generateDays`) stay UTC-anchored. Until 2026-08-14 today came from `new Date().toISOString()` on both ends: at 9pm CST the board read Saturday and spillover moved tasks early.
  - **Frontend:** `getTodayKey()` is `new Date().toLocaleDateString('en-CA')` (formats as `YYYY-MM-DD`). `getTomorrowKey()` builds off that key.
  - **Backend:** every request-scoped today goes through **`todayKeyFor(req)`**, reading an **`x-tz` header** (sent by `api()` on every call) and formatting through `Intl`. Unknown/absent zone falls back to UTC. No schema change, nothing cached.
  - Sites: spillover (`GET .../tasks`), `due_today` on `GET .../projects`, subtask return, calendar sync's `todayKey`. Any new server "today" belongs there too.
  - Not covered on purpose: `monthKey()` for the AI budget is still UTC.
