# Lists: quick lists and the Lists page

> Read when touching "list …" tasks, the pink list box/pane, /lists, shelve/unshelve or sync-master. Moved out of CLAUDE.md verbatim on 2026-09-30; keep adding here, not there.

### Quick lists ("list …" tasks)
- A task starting with **"list"** (`/^list\b/i` — `isListTask()` frontend, same regex in `server.js` and `ai.js`; `\b` keeps "listen…" out) gets a different pane: the user's **quick list on top, AI "Suggestions" below**.
- **On the day board a pending list is a box, not a row (2026-09-15).** `renderListBox()` puts a `.list-box` right under the add-task input: the list's name as an input placeholder (`listBoxLabel()` rewrites "list things to take to Seattle" as **"list: things to take to Seattle"**), same white box as "Add a task…", **placeholder in pink** (`#db2777`, `#f472b6` dark — the lighter dashboard pink is under 3:1 on white; grey at the input's brightness read as a second input, Kevin 2026-09-15), plus a ▾ on the right. **Typing into it adds the item and opens the list** (`addQuickListItem(id, text, 'box')` keeps focus in the box); **▾ opens or closes it** without adding. The pane is the same list pane a row used to open. `isListBoxTask()` decides (pending, own, non-calendar, not awaiting/review); inbox and review lists stay rows because they need their answers. Box tasks are excluded from `pendingTasks` and from `orderedDayTasks()` slot math (the order route appends omitted ids). **Trade accepted for now:** a boxed list has no →, lock, drag, day counter or hover-key gestures; it still spills forward and counts against the day's 7. List view still shows it as a row.
- **A day's list is open by default (2026-09-16).** `renderBoard()` rebuilds `autoOpenListIds` every render: the day's first list box opens on its own when no task pane on that day is in `expandedTaskIds`, the briefing isn't holding today's slot, and the person hasn't shut it with ▾ (`closedListIds`, per page load — ▾ again reopens). Clicking a task replaces the list with its pane; closing that pane brings the list back. Subtasks for an auto-opened list load lazily (`loadingSubtasksFor` guard; a failed read stores `[]` so the render can't loop). `listBoxOpen(id)` is the one test for the box's open state.
- **The list pane has a thin pink border** (`.subtask-pane.list-pane`, the box's `#db2777` / `#f472b6` dark) so the box and its pane read as one thing (2026-09-16).
- **The entry slot sits at the top of the list pane** (one `.quick-slot` under the header, like the day card's add-task box); the three dashed slots under the items are gone. **No cost total on a list** and **a list never researches** (`!isListTask` in the generate route's `wants`): the pass had priced a packing list off retailer pages. The list prompt in `ai.js` forbids products for sale, prices and store links — a link only when it identifies the thing itself (a film, a place).
- **No rail and no headings (2026-08-16).** User items are `assignee_type 'human'`, rendered **checkbox + text**; suggestions are **↑ + text**; a dashed divider (`.list-suggestions`) is the only separator. The assignee emoji is gone.
- Below the user's items, dashed **blank slots** (`.quick-slot`): 3 to start, then always one (`Math.max(3 - count, 1)`). Enter creates the subtask and refocuses the next slot (`addQuickListItem()`).
- **Suggestions**: AI rows forced to `assignee_type 'ai'` server-side. ↑ PUTs `assignee_type: 'human'` — the row moves into the list and survives regeneration. **↺ replaces every unadopted suggestion.** **An empty circle on each suggestion deletes it (2026-09-16)** — the board's completion idiom, row reads circle · ↑ · text (`.subtask-dismiss`, `dropSuggestion()`, the one frontend caller of `DELETE /api/subtasks/:id`). A × was built first and replaced within the hour. Ordinary step rows still have no delete.
- **List panes build their own rows and never call `subtaskRow()`** — no promote arrow, 🔎 or emoji by accident. This retired the `moveUp` parameter and its `pending.map(subtaskRow)` trap; the builder takes one argument.
- **If a "list" task shows the ordinary pane, check the wording:** "list stuff for taco night" gets the list pane; "taco night list" gets a normal pane whose ↑ promotes to the board.
- **Regenerating deletes only AI rows** (`DELETE … WHERE assignee_type='ai'`) and returns the **full** subtask set (the frontend replaces its cache with the response).
- `ai.js` `buildPrompt()` branches on the regex: list tasks ask for **7 concrete candidate items** as bare JSON strings; the parser accepts strings or `{description}`. `generateMockSubtasks` has a matching branch.
- History: v1 was a Family Feud board; Kevin cut it within hours. Playful mechanics are the first thing he trims — ship the minimal interaction first.

### The Lists page (/lists, 2026-09-22)
- **A list you'll want again shouldn't expire with the day it was written on.** "list things to take to Seattle" on Sep 19 becomes **Travel**, kept on `/lists`, and dropped onto any day as a fresh copy.
- **Board → page MOVES; page → board COPIES** (Kevin's calls, 2026-09-22). The master is a library card, not a token: it stays on the page, and **every copy starts with nothing ticked**, so ticking "passport" off in Seattle never erases it from the list he keeps. **AI suggestions don't follow** — they were a board-time helper; shelving drops them along with anything already ticked.
- **`tasks.shelved` (0/1) is the whole mechanism.** A shelved list is an ordinary task row with ordinary subtasks as its items — no second store, no second item type — so the page reuses `POST /tasks/:id/subtasks`, `PUT|DELETE /subtasks/:id` and `PUT /tasks/:id { description }` (rename) untouched. The cost is that **every board query must carry `COALESCE(shelved,0) = 0`**: spillover, autolock, the board read, `due_today`, the List view, the shared board, `findDayWithCapacity()` and `bumpableTaskOn()` (same trap as `t.goal` — a hand-listed SELECT or a COUNT that forgets it puts a phantom row back on a day).
- **Routes:** `GET|POST .../lists`, `POST /api/tasks/:id/shelve`, `POST /api/tasks/:id/unshelve { scheduled_date, project_id }`. Unshelve refuses a past day, and **skips `findDayWithCapacity()`** — a list is a box under the add-task input, not one of the day's seven rows, so it neither fills a day nor bumps anybody. Shelve also splices the row out of its series and clears `locked`/`goal`/`repeat_rule`/`due_date`/`position`.
- **The name carries the prefix across the boundary.** The board decides a list pane by reading the description (`LIST_TASK_RE`), so the master is filed as **"Travel"** (`listNameFrom()` strips a leading `list`/`list:`) and the copy goes back as **`list: Travel`** (`boardDescriptionFor()`). Rename the master to anything; the trip back re-prefixes.
- **A boxed list keeps → and 📅, never drag (Kevin, 2026-09-22).** They carry the *same* `.task-arrow` / `.task-lock` classes a task row uses, so the existing click wiring, the lock popup and **hover-the-arrow-and-press-1-9** work with no second code path; the box shows 🔒 when locked. **The inline-edit resolver has to exclude them** — `tryInlineEdit()` runs in the capture phase and would otherwise swallow Shift+Click-the-arrow (+1 week) and rename the list instead.
- **A copy pushes its edits back up: `Update “Travel”`** replaces the footer's Keep button whenever the row has a master (`tasks.list_master_id`, set at unshelve, `ON DELETE SET NULL` so deleting the master just unlinks the copy). `POST /api/tasks/:id/sync-master` makes the master's items **the copy's items — all of them, ticked or not, and all unticked on the master**: a tick on a copy means packed, not "drop it from the list I keep" (Kevin's call). Removal for good is a Lists-page gesture only. **The name is deliberately not synced** — renaming a copy "list: Seattle trip" for one trip must not rename the list you keep. A copy with a master is never offered Keep, or the board would grow a second "Travel".
- **`listMasterOf` (taskId → {id, name}) is filled from both task reads** — the board's and the List view's — because a pane opens on either; both SELECTs carry `t.list_master_id` and a `LEFT JOIN tasks lm` for the name (the usual hand-listed-SELECT trap).
- **The doors are sentences, not glyphs.** The list pane's footer (`.list-foot`, a dashed pink rule) holds two: **`Keep on the Lists page`** / **`Update “Travel”`** on the left and **`Delete`** on the right (`.list-keep` truncates a long master name; the tooltip carries it whole). A 178px column has room for four words, and these are the controls that act on the *whole* list rather than a row of it. The page's own door is a **lists icon in the header, right of the dashboard icon** (Kevin, 2026-09-22 — the group reads notes · dashboard · lists, and its leftmost, `#notesLink`, carries the `margin-left: auto` that floats the middle group).
- **`Delete` is the only way to get rid of a list from the board.** A boxed list has no completion circle, and ticking items off empties it one line at a time — without this, a list you were done with could only be pushed to another day forever. It confirms first, and on a copy both the confirm and the toast say the master on the Lists page is untouched. (Ordinary step rows still have no delete; this deletes the *task*, via `DELETE /api/tasks/:id`.)
- **The page** (`public/lists.html`, one static file like `/notes`): composer on top (Enter names a new list), CSS-columns masonry of cards with a **pink left edge** (the list's colour, same as the board's box and pane). Per card: click the title to rename, an **empty circle removes an item** (the suggestion-dismiss idiom — a master has nothing to tick off; ticking is what you do to a copy, on a day), **click an item to edit it in place** (Enter or blur saves, Escape cancels — the board's inline-edit idiom, not a `prompt()`), an add-item slot, then board + day pickers and **Put on the board**, with Delete opposite.
