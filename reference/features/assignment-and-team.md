# Assignment, review rows and the team

> Read when touching assign/accept/return, review rows, handoff chips, shared boards, Tessa or the demo team. Moved out of CLAUDE.md verbatim on 2026-09-30; keep adding here, not there.

### Assigning a step to someone new (the + button)
- The team popup's **+ New** creates a person and hands them the thing you were assigning. It was **dead on every reachable path** until 2026-08-13: the handler ran `if (activeTaskId) showAddUserModal(activeTaskId)`, but `showSubtaskAssignPopup()` nulls `activeTaskId`, and `showTeamPopup(e, taskId)` **was defined but never called**.
- Fix threads a `target` of `{ taskId }` or `{ subtaskId, taskId }` through `showAddUserModal` → `pendingAssignTarget` → `createUserAndAssign`, branching to `assignSubtask()` or `assignTaskToMember()`. Both server routes already existed.
- Two latent bugs fixed on the same path: the modal called `newUserName.focus()` while the overlay was `visibility: hidden` (**Safari ignores it** — now deferred 50ms), and "Done" read `newUserCreated.name` *after* `hideAddUserModal()` nulled it.
- `showTeamPopup()` stays as the re-entry point for whole-task assignment.

### Assignment Flow (accept / return, since 2026-08-20)
- **Two ways to hand work over (2026-08-21):** clicking the assignee emoji on a subtask assigns that step; a hover-reveal 👤 on every pending board row (beside the 📅 lock, `.task-send`) forwards the **whole task** — both open the same team popup. Hover-reveal is the board's sanctioned carve-out from "no hidden affordances".
- **Tessa is the AI teammate** (`users.is_ai`, seeded by the demo-team route with role "AI Assistant"). She renders with a 🧠 avatar on a neutral sky tint everywhere people render (`avatarGlyph()`/`avatarBg()` — the 🧠 emoji is pink, so it needs a non-person-color circle), and **work assigned to an AI auto-accepts** in both assign routes (an AI has no inbox to deliberate over). Toast: "Tessa is on it" vs "Sent to Margo — awaiting their answer". She can still *return* work; real dispatch will hang off `is_ai`. **The pink-brain-on-sky-tint avatar is settled**: a white-brain SVG on accent blue was built, shipped and reverted the same day at Kevin's request (2026-08-21). Don't re-"fix" it.
- Clicking the assignee emoji on a subtask assigns it (replaced the old Cmd+Click). Assigning a subtask creates a task on the recipient's board; `subtasks.assigned_task_id` links the two.
- Once assigned, the task leaves the sender's day pane and project page (`owner_id` is rewritten — the row *moves*; no `assigned_to` column). **Both assign routes guarantee the recipient can reach the row**: task-level assign auto-adds them to the project (subtask route already did), and a handover from a NULL-project task (a calendar row's step) adopts the recipient's first board. Task-level assign is refused on `source = 'calendar'` rows.
- A person assigned to a project gets a project page pre-filled with the project name if not already on it.
- **A handed-over task arrives "awaiting": `assigned_by` set + `accepted_at` NULL.** Renders as an amber inbox row (dashed circle, `from <name>`, permanent ✓ accept and ↩ return — no hover-reveal: this is the one row that is a question). Every work affordance withheld — no completion (server 409s `completed: true` in `PUT /api/tasks/:id`), no arrow, drag, lock, reorder digits, or subtask pane. Day board and List view.
- **Awaiting rows show on every board of the recipient** (a third OR in the `GET .../tasks` project filter, like calendar rows). **The spillover's project scope carries the same OR** — or an unanswered handover strands on a past date no day card renders. Excluded from reorder slot math (`orderedDayTasks`). Accepting (`POST /api/tasks/:id/accept`) stamps `accepted_at` and settles the row onto its own project's board — `acceptTask()` refetches tasks *and projects*, and the toast says where the row landed if not this board.
- **Returning is an answer, not a bounce:** `POST /tasks/:id/return` stamps `accepted_at` on the way back, so the sender gets work labelled "from Margo", never an inbox item. A returned step is un-assigned in the sender's pane (via `assigned_task_id`). Re-assigning an accepted task resets `accepted_at` to NULL.
- **Finished handed-over work comes home FOR REVIEW (2026-08-21).** On completion the row moves back to the sender's board as a **pending row with `completed_by` set — "review" IS that pair** (`isReview()`: pending + completed_by + not awaiting). It renders in its own **"From teammates" section above the completed divider** (`.review-section`), blue (amber is *their* question, blue is *yours*), full-color text, empty circle, quiet `~Margo`, and four permanent answers (**↑ reclaim in the arrow slot** — circle · ↑ · text, using the locked-row `padding`/negative-`margin` idiom so the text column lines up): **circle** accepts the completion (joins completed with the `~Margo` no-strike `done-elsewhere` treatment), **↑ reclaim** takes it back (`completed: false` clears `completed_by`, un-assigns/severs any linked pane step), **👤** sends it elsewhere, **↩ send-back** re-assigns it to whoever did it — the ASSIGN route, not return, so `return_when_done` re-arms. **Clicking the row's text opens its task page** (no subtask pane on review rows). Review rows are pending so they **spill forward to today**, show in List view (label + circle + page-click), and aren't hidden by focus mode. The pane chip reads 'done' off `completed_by`; **the linked step completes only when the sender ticks**. Plumbing: gated on **`tasks.return_when_done`** (set at assign, cleared at return — `assigned_by` alone can't tell "work someone gave me" from "my work that came back"), **`tasks.completed_by`** (not backfilled), move runs after `spawnNextRepeat`, lands on a board the sender belongs to (`firstBoardOf()`), stamps `accepted_at`. Completer sees "Done — sent back to Kevin". Excluded from reorder slot math and hover-key gestures.
- **Sent work is never greyed (2026-08-21): grey is reserved for finished.** It took THREE removals to un-grey one category (`.assigned-tasks` opacity, `.task-item.forwarded .task-description` color, `.subtask-item.assigned-subtask` opacity) because dimmings were stacked. When un-greying, grep every layer first. The amber ➔ circle, "→ Margo" label and handoff chip carry the sent state.
- **The sender's pane shows handover state** on each assigned step: a `.subtask-handoff` chip (avatar + "Margo · not accepted yet / accepted / done") from `assignment_state`, derived server-side in `GET /tasks/:id/subtasks` (awaiting amber, accepted blue, done grey — no green). **The chip follows onward chains**: Margo assigning on to Jay repoints the step (and dependents) at Jay; a mid-chain return repoints; a hop landing back on the original sender's board clears the chip. "Return" goes to whoever handed it to *you*, so the way home from a chain is an assign back to the sender.
- Pre-feature assignments were backfilled `accepted_at = updated_at` on the migrating boot.

### Shared boards + the demo team (2026-08-20)
- **`users.share_board` (default 0) gates `GET .../users/:slug/shared-board`** — 403 until shared. With no auth this is a product rule, not a security boundary; it's the seam real permissions go in. `users.role` is display-only.
- **The team lives in the account popup** (click the user·project chip): a "Team boards" roster (avatar, name, role, greyed "private" when unshared) plus "Share my board with the team" / "Make my board private" (`PUT .../users/:slug/share`).
- **A teammate's board opens as the team view** (`viewMode 'team'`, `#teamContainer`): banner (avatar, name, role, the sharing rule, plus "N things you sent are still unanswered"), person tabs for everyone shared, seven day cards. **Read-only by construction, deliberately not a mode of `renderBoard()`** — a board with everything disabled reads as broken. The route runs **no spillover and no calendar sync**, isn't project-filtered, folds past-due rows onto today in the response only — except past calendar events, which are dropped. Rows order with the position NULL-last idiom. Awaiting rows carry "Waiting on ⟨name⟩" if you sent it, else "Sent by ⟨name⟩ · not accepted". The project bar hides (`visibility: hidden`); the view toggle becomes "back to your board".
- **`POST /api/companies/:subdomain/demo-team` seeds Margo (Accounting), Jay (Product Marketing), Yarwen (CTO) and Tessa (AI Assistant, `is_ai = 1`)** — each shared, with a board and a seeded week. Idempotent (existing teammate reused; week only seeded onto an empty board); reachable from the account popup's "Add the demo team" row, offered until all three exist (case-insensitively). **A pre-existing user with those names is adopted only if unused (zero tasks)** — a real Margo must not be force-shared.
- **`loadUsers()` runs at signup and session restore** and keeps `currentUser` fresh. It was defined-but-never-called — after reload `allUsers` held only you, emptying the assign popup and roster.
