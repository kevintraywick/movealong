# Move Along

A task management app that moves ideas into action and reduces decision-fatigue. It does this by letting users immediately postpone (move) a task or subtask, mark it complete, or assign it to a human or AI agent.

## Vision

Two goals:
1. **Move ideas into action** — When a task is added, Claude immediately populates a subtask pane with the steps needed to complete it, so the user instantly sees what's involved.
2. **Reduce decision-fatigue** — Every subtask has a default assignee (AI or human), and the user can assign with a single click. AI agents research options, fetch prices, check weather, and return actionable information so the user doesn't have to.

Tasks can also be sent to an AI agent for execution, not just humans. Cross-user collaboration (assigning to other people) is currently back-burnered — focus is on the single-user + AI-agent loop.

## Core Concepts

### Projects
The basic unit is a **project page** (the 30-day calendar board). A user can create as many projects as they want using the same username — e.g., "personal", "doghouse", "financial". Each project is its own board.

### Tasks and Subtasks
- When a task is added to a day, a **subtask pane** opens beneath the day pane.
- Claude populates the subtask pane with up to **7 subtasks** — the steps needed to complete the task (prompt asks for 5-7; the generate-subtasks endpoint hard-caps AI and mock lists at 7).
- After the initial subtasks are shown to the user, Claude runs a deeper analysis using agents to review proposed solutions, fetch relevant data (Amazon prices for purchases, weather for outdoor/travel tasks, etc.), and refines the subtasks into a solid plan.
- Each subtask has an **emoji indicating the default assignee**: brain (🧠) for AI agent, woman (👩) for human. The user assigns by clicking the emoji.
- **Dependent subtasks** appear indented (3 spaces) under their parent in light grey font. They move with the parent if assigned.

### Subtask Quality: Actionable, Not Generic
Subtasks must be **specific, actionable, and research-backed** — never vague project-management filler.

**Bad subtasks** (too generic):
- "Define requirements and scope"
- "Research materials and tools needed"
- "Create a detailed plan"

**Good subtasks** (actionable, with research):
- "Pick a location — sunny, 5-10 ft high, near trees (birdsonly.com/placement-guide)"
- "Choose target birds for your area (audubon.org/native-plants/98101)"
- "Decide: buy plans online ($5-15 on Etsy) vs design your own"
- "Get materials — cedar boards, screws, waterproof glue (Home Depot list)"

**Principles:**
1. **Prefix with a mini-label** when helpful: "Project plan:", "Decision:", "Research:", etc.
2. **Include links** — AI subtasks should link to real, relevant websites (retailer searches, guides, location-aware resources) so the user can click and act immediately.
3. **Surface the actual decisions** — don't say "plan the menu"; say "Decide: cook vs cater vs potluck (Thumbtack caterers near you)".
4. **Be domain-specific** — a birdhouse task should mention bird species and wood types, not generic "gather materials".
5. **AI-assigned subtasks do research** — when an AI agent runs a subtask, it should return concrete options, prices, links, and comparisons — not summaries.

### Two-phase subtasks (draft now, research behind it)
- Adding a task runs **phase 1**: a fast reasoning-only call that returns 7 steps in seconds. The point is to get the user's brain engaged immediately, not to be right yet.
- **Research is opt-in, and since 2026-08-16 it is chosen per step.** `projects.research_enabled` defaults to **0**, and the trigger is the **🔎 on each step's rail** (`POST /api/subtasks/:id/research`). The pane-wide "Research these steps" button is gone: researching all seven at once decided *for* the user which steps were worth money, when the whole point is that only two or three of them are. Flip the **🔎 Research switch in the header** (beside 🧠 Assistant) and every new task researches automatically instead. Off by default because at ~$0.10 a researched task, auto-researching everything empties a $5 board in about a week — the arithmetic, not taste, is what settled this.
- **↺ never researches**, switch or no switch (`req.body.regenerate === true`). Topping up one row costs a whole search budget (`max_uses` is per call, not per row), so a regenerate-happy user would be the most expensive user in the app.
- **Phase 2 (`runResearch()` in `server.js`) runs behind the HTTP response**, fire-and-forget, using the Anthropic `web_search` tool, and rewrites those rows **in place**. It never adds, removes or reorders steps: results are matched back **by index**, and every row is re-read immediately before writing, so a row the user ticked off or promoted mid-flight is skipped rather than resurrected. This re-check is load-bearing — research takes 15-60s and the user is looking at the pane the whole time.
- **A step is replaced outright only at ≥ 0.8 confidence** (`RESEARCH_REPLACE_CONFIDENCE`). The model returns `refined` (always) plus `illogical`/`confidence`/`replacement`; the gate lives server-side where it's auditable. Ordinary vagueness is refined, never replaced — swapping out a row the user is currently reading is disruptive, so the bar for it is high.
- **`subtasks.provisional` is the "awaiting research" flag** and is what the frontend poll watches. It is set only when phase 2 will actually run — the on-demand endpoint sets it on pending unresearched rows before dispatching. It no longer changes how a row looks: with research opt-in, a draft is a finished state, not a degraded one.
- **`subtasks.researched` marks rows the pass actually rewrote**, and those render **light blue** — a row tint (`#f0f9ff` + inset `#7dd3fc` edge) with blue-tinted text, *not* blue text alone. AI steps are full of `.task-link` anchors at `#0284c7`; blue text wrapped around blue underlined links is unreadable. Any future "colour the text" request in the subtask pane hits this same wall.
- **The frontend polls** (`pollResearch()`, 3s, capped ~2 min) while an open pane holds a provisional row — there are no websockets and no queue in this server. Close the pane and research still finishes server-side. `repairInterruptedResearch()` clears the flag on boot, since a restart mid-research would otherwise leave rows greyed forever with nothing left running to clear them.
- **`runResearch` must call `flushDb()` itself** — same trap as the calendar sync: `res.on('finish', flushDb)` already fired for the request that started it.
- **Per-step research runs at `SINGLE_STEP_SEARCHES` (2), not the whole-task 5.** `max_uses` is per *call*, so a single row at the batch budget would cost as much as researching all seven together — seven one-at-a-time clicks would be 7× the batch. Now that this is the pane's primary control, its unit cost is the one that compounds. It also **writes the same three-state cost fields** as `runResearch()`; without that, a row researched from its own button silently got no price while the same row researched from the pane did. It skips cost triage — triage exists to aim a shared search budget across seven rows, and there is nothing to aim with one.

### Keeping the pane at seven
- **Regenerate (↺) tops up and drafts only; it does not wipe and it does not research.** It used to run `DELETE FROM subtasks WHERE task_id = ?` and destroy steps the user typed themselves. Now every pending row survives, only the freed slots are refilled, and the kept steps are shown to the model so it doesn't re-propose them. A full pane returns `full: true` and spends nothing.
- **There is deliberately no delete affordance on a subtask row**, so **ticking a step off is the only way to free a slot**. The `DELETE /api/subtasks/:id` endpoint exists but nothing in the frontend calls it.
- **A list pane is exempt from the top-up.** "My list" and "Suggestions" are separate sections, so capping the two together would starve suggestions; its AI rows are still replaced wholesale.
- **Hover a step and click ↑ to promote it onto the board** as a real task. It lands on the **parent task's day, not today** — the pane may be open under next Tuesday because that's when the user plans to do it — goes through `findDayWithCapacity()`, and leaves the pane, which frees a slot. That's the escape hatch when seven isn't enough.
  - ↑ is **always visible** since 2026-08-16. It used to hover-reveal (the `.task-lock`/`.task-unlink` idiom), but a control that only appears once you are already pointing at the row can't be discovered by looking, and in the rail it costs nothing to leave on. **The board's hover-reveals stay** — rows there are one line and genuinely can't spare the width. It is **withheld on list-pane suggestion rows**, where ↑ already means "move to my list" — two arrows with two meanings in one pane would be indefensible.
  - Promoting lifts any dependents to the row's own parent first; `parent_subtask_id` is `ON DELETE CASCADE`, so skipping that step destroys them.
  - **The promoted task lands directly under the task it came out of, and its circle carries a dot.** `tasks.promoted_from` records the source; `placeTaskAfter()` splices the new row in at `parent.position + 1` and renumbers that day. Hovering the promoted row tints its source row (`.source-highlight`) — the same hover-to-reveal-the-relation idea as the series threads, but a plain tint, since it is one edge and both rows are usually in the same card. **Indenting or greying it would have been wrong**: that is the subtask pane's vocabulary for dependents, so it would say the row *is* a subtask of the row above, which is exactly the confusion the cue exists to prevent. The dot uses `.task-circle:empty::before`, so it is withheld the moment the circle has something else to say (a series countdown, the completed check).
  - Placement is skipped when `findDayWithCapacity()` overflows the promoted task onto **another day** — there is nothing to sit under there, so it appends as before and keeps the dot and the hover link.

### AI budget (per board, per month)
- `projects.ai_budget_usd` — whole dollars, **default $5**. Whole dollars on purpose: a cents-level control is exactly the decision this app exists to save people from.
- **The on/off control is the 🔎 Research switch in the header** (`#researchSwitch`, same `.assistant-switch` markup as 🧠 and 📅). State is **per board** (`projects.research_enabled`), unlike its two neighbours which are per browser — it spends *this* board's money, so it repaints from `refreshBudget()`.
- **Turning it ON opens a cost dialog first** (`#researchWarnModal`): ~$0.10 a task, this board's spend so far, a **Change budget** link, and a **Don't warn me again** checkbox writing `localStorage['movealong.researchwarn'] = 'off'` — per browser, not per board, because it records that this person has read the price. Turning it **off** never warns; only spending does.
- **The quiet budget line under the board (`#budgetBar`) is gone** (2026-08-14) — the bottom of the page is not navigation. Its two jobs moved into the header: spend is in the switch's `title` tooltip, and **Shift+Click the switch edits the budget** (the same idiom as Shift+Click on 🧠 for the AI access key). That Shift+Click is now the *only* permanent path to the budget once a user dismisses the dialog — the over-budget toast is the other reminder it exists.
- **It gates research only.** Phase 1 always runs — a task the user just typed must always come back with something — so an exhausted board still drafts steps, marks them final, and says so in the pane (`research_status = 'over_budget'`).
- Spend is metered from the API's own `usage`, **including `server_tool_use.web_search_requests` at $10/1000**, and written one row per call to `ai_usage`. An audit trail, not a counter: the first question anyone asks a budget is where it went. Rates live in one constants block at the top of `ai.js` — nothing reads a live price list, so verify them if the numbers ever look off.
- Rough unit cost: **~$0.10 per researched task** at `max_uses: 5` — about half of it is the searches themselves ($0.01 each), which is why `max_uses` is the real cost lever, not the token count. $5 buys roughly 50 of them. (A researched task now makes two calls, not one: the Haiku cost-triage adds a fraction of a cent and doesn't move that arithmetic.) **Since research went per-step, the batch is no longer the common path:** seven steps researched one at a time is ~$0.21 (7 × 2 searches) against ~$0.10 for the whole-task pass. Cheaper per click, more expensive if someone researches everything — the intended trade, on the bet that only two or three steps in a pane are worth it.
- **The rates in `ai.js` are hand-maintained and per-model.** They are not stable across a family: Sonnet 5 is $2/$10 per MTok where Sonnet 4.6 and earlier were $3/$15. Re-check the pricing page whenever `MODEL` changes, and note that cache reads bill at 0.1x base input and writes at 1.25x — folding those into base input overcharges 10x on reads.
- **A third-party search agent was evaluated and declined (2026-08-16):** Mixedbread's *Toast 1*, a specialised search agent at $0.016–0.023/query and ~8s median latency. Its headline "10x cheaper than a frontier model" compares against using a frontier model *as the search agent* — which this app doesn't do; Sonnet 5 + the server-side `web_search` tool is already the cheap configuration, so the realistic saving is a few cents a task against a $5/month cap, in exchange for a second vendor and a second failure mode in the one path the user watches live. **Revisit only if** research latency becomes the complaint (8s would delete `pollResearch()` entirely) **or** step pricing pushes a task past what `max_uses: 5` can cover. Two things to settle first: whether it searches the open web or only a corpus you index with them (its flagship benchmarks are document retrieval), and whether it can return the index-matched structured objects the research pass needs — if it only returns curated context, it replaces the search half of the call, not the call.
- **`AI_LIMIT_*` and this budget are not the same thing.** Those are abuse brakes on a public deployment (per IP, per day); this is the owner's own dollar cap on research.
- `web_search` takes `user_location`; the only location this app knows is the IANA zone captured when a **calendar feed** was connected, which is enough to localize "stores near me" without asking for an address.
- Calendar rows carry `project_id = NULL` and so have no board to bill — they are never researched.

### What a step costs (materials, labour, services)
- **Two different costs, never one number.** `ai_usage` is metered actuals from the API's own `usage` block — auditable to the cent. The `subtasks.cost_*` columns are an *estimate about the world*, which is uncertain, local and time-varying. They render on the same screen and must never be added together; a single figure covering both would be a lie about the half that isn't measured.
- **Written only by the research pass, as extra fields on each verdict — not a second pass.** `max_uses` is per call, so a separate cost call would double the search budget (and roughly double the ~$0.10) for information the model that just searched "cedar picket price" already had.
- **A Haiku 4.5 triage call runs first** (`triageCosts()` in `ai.js`), labelling each step `material | labor | service | none`. Most steps are `none` — "Decide: cook vs cater", "Pick a location" spend nothing — and the labels ride into the research prompt so the searches concentrate on the two or three rows that do. **The point is not the token saving** (fractions of a cent) but the search budget, which is the real cost lever. Triage failure is caught and logged: research then decides for itself, exactly as before it existed. It gets its **own `ai_usage` row** (`kind = 'cost_triage'`) because a budget's first question is where the money went.
- **Ranges only**, never point estimates, and `cost_basis` ("24x 6ft cedar picket at $4.28") is **required** — it's what makes a number checkable rather than merely plausible. `cost_source_url` and `cost_as_of` ride in the chip's tooltip; a price with no date is worse than no price.
- **Three states, and the difference is load-bearing:** a priced row; `cost_kind = 'none'` (research ran, this step spends nothing — an *answer*); and `cost_kind = NULL` (unknown — never researched, or the estimate came back too shaky). The pane's total prefixes **≥** whenever any pending row is NULL, because a total that silently omits the unknowns understates.
- **The confidence gate lives in `runResearch()`**, beside the 0.8 replacement gate, where it's auditable. `COST_MIN_CONFIDENCE` is **0.5** — deliberately lower than `RESEARCH_REPLACE_CONFIDENCE`, because that gate guards *replacing text the user is reading* while this one only guards adding a figure they can take or leave, and a range already carries its own uncertainty. Below it the estimate is dropped and the row shows no price.
- **Rendering:** a grey chip after the step text (`.subtask-cost`), an `<a>` when a source URL exists; the task total sits opposite the title in the pane header (`.subtask-cost-total`). Whole dollars, matching the budget control's own reasoning — "$91.40–$127.75" claims a precision an estimate does not have.
- **`ai.js` rates are now a per-model `RATES` map**, because two models bill in one flow. Re-check both when either model changes; `meterUsage(data, model)` takes the model explicitly.

### Assigning a step to someone new (the + button)
- The team popup's **+ New** creates a person and hands them the thing you were assigning. It was **dead on every reachable path** until 2026-08-13: the handler ran `if (activeTaskId) showAddUserModal(activeTaskId)`, but `showSubtaskAssignPopup()` explicitly nulls `activeTaskId`, and `showTeamPopup(e, taskId)` — the task-level entry point — **is defined but never called**. So the only live trigger is the subtask emoji, where the guard could never pass.
- The fix threads a `target` of `{ taskId }` *or* `{ subtaskId, taskId }` through `showAddUserModal` → `pendingAssignTarget` → `createUserAndAssign`, which branches to `assignSubtask()` or `assignTaskToMember()`. Both server routes already existed; only this frontend path was task-shaped.
- Two latent bugs on the same path, both live once the + is reachable: the modal called `newUserName.focus()` synchronously while the overlay was still `visibility: hidden` (**Safari ignores it** — the documented modal trap, now deferred 50ms), and the "Done" button read `newUserCreated.name` *after* `hideAddUserModal()` had nulled it, throwing every time.
- `showTeamPopup()` is left in place as the re-entry point for whole-task assignment when collaboration comes off the back burner.

### Assignment Flow (accept / return, since 2026-08-20)
- **Two ways to hand work over (2026-08-21):** clicking the assignee emoji on a subtask assigns that step, and a hover-reveal 👤 on every pending board row (beside the 📅 lock, `.task-send`) forwards the **whole task** — both open the same team popup. The 👤 is the gesture `showTeamPopup()` sat waiting for since collaboration was back-burnered; the popup and `POST /tasks/:id/assign` always existed, only the click was missing. Hover-reveal is the board's sanctioned carve-out from "no hidden affordances" (one-line rows can't spare a second permanent icon).
- **Tessa is the AI teammate** (`users.is_ai`, seeded by the demo-team route with role "AI Assistant" and her own seeded week). Two behaviours hang off the flag: she renders with a 🧠 avatar on a neutral sky tint everywhere people render (`avatarGlyph()`/`avatarBg()` — the 🧠 emoji is pink, so it needs a non-person-color circle), and **work assigned to an AI auto-accepts** in both assign routes — an AI has no inbox to deliberate over, and a human clicking accept on the assistant's behalf would be an approval step the app exists to delete. The assign toast says so: "Tessa is on it" vs "Sent to Margo — awaiting their answer". She can still *return* work (the future agent's "here's what I found" path); real dispatch will hang off `is_ai`.
- Clicking the assignee emoji on a subtask assigns it (replaces the old Cmd+Click flow). Assigning a subtask creates a task on the recipient's board; `subtasks.assigned_task_id` links the step to that task so the two ends can see each other without matching description text.
- Once a task is assigned, it is removed from the sender's day pane and project page (`owner_id` is rewritten — the row *moves*; there is still no `assigned_to` column). **Both assign routes guarantee the recipient can reach the row once accepted**: task-level assign auto-adds them to the task's project (the subtask route already did), and a handover from a NULL-project task (a calendar row's step) adopts the recipient's first board — a NULL there would make the row unreachable the moment they accept. Task-level assign is refused on `source = 'calendar'` rows (the feed would duplicate them on next sync).
- A person assigned to a project gets a project page pre-filled with the project name if they aren't already on the project.
- **A handed-over task arrives "awaiting": `assigned_by` set + `accepted_at` NULL.** It renders as an amber inbox row (dashed circle, `from <name>`, permanent ✓ accept and ↩ return buttons — no hover-reveal: this is the one row on the board that is a question, and its answers must be visible by looking). Every work affordance is withheld — no completion (server 409s `completed: true` too, in `PUT /api/tasks/:id`), no arrow, no drag, no lock, no reorder digits, no subtask pane. Day board and List view both.
- **Awaiting rows show on every board of the recipient**, same mechanism-by-analogy as calendar rows (a third OR in the `GET .../tasks` project filter): an inbox item hidden behind the sender's project tab is not an inbox. **The spillover's project scope carries the same OR** — a cross-project inbox row must spill from every board too, or an unanswered handover strands on a past date no day card renders. They are excluded from reorder slot math (`orderedDayTasks`) like calendar rows. Accepting (`POST /api/tasks/:id/accept`) stamps `accepted_at` and settles the row onto its own project's board — `acceptTask()` refetches tasks *and projects* (the handover may have put you on a board this session never loaded) and the toast says where the row landed if that isn't the board you're looking at.
- **Returning is an answer, not a bounce:** `POST /tasks/:id/return` stamps `accepted_at` on the way back, so the sender gets their task back as work labelled "from Margo", never as an inbox item for their own task. A returned handed-over step is also un-assigned in the sender's pane (via `assigned_task_id`). Re-assigning an accepted task resets `accepted_at` to NULL.
- **Finished handed-over work comes home (2026-08-21).** When the recipient completes a handover, the completed row moves back to the sender's board, dated the day it finished — the landing IS the "Margo finished it" notification, state rather than a message (there are still no websockets and no notification queue). It renders **check in the circle, greyed text, NO strikethrough** (`.task-item.completed.done-elsewhere`) with a "done by Margo" label — the strike is the mark of a task *you* ticked; this row is news, not your own crossed-out item. Load-bearing details: the bounce is gated on **`tasks.return_when_done`** (set by both assign routes, cleared by return), because `assigned_by` alone can't tell "work someone gave me" from "my work that came back" — without the flag, completing a *returned* task would bounce it onto its returner's board. **`tasks.completed_by`** records who did the work (cleared on reopen); deliberately **not backfilled**, so pre-feature assignments never bounce. The move runs after `spawnNextRepeat` (a repeat's next instance stays with the completer), lands on a board the sender is actually a member of (`firstBoardOf()` fallback), stamps `accepted_at` (never an inbox row), and **auto-completes the linked subtask + its dependents** in the sender's pane — the finished row and a still-pending step would be one fact told two ways. The completer sees "Done — sent back to Kevin" and the row leaves their board.
- **The sender's pane shows the handover state** on each assigned step: a `.subtask-handoff` chip (avatar + "Margo · not accepted yet / accepted / done"), driven by `assignment_state`, which `GET /tasks/:id/subtasks` derives server-side from the linked task (awaiting amber, accepted blue, done grey — green is banned, and done needs no attention anyway). **The chip follows the task through onward chains**: Margo assigning her handover on to Jay repoints the step (and its dependents) at Jay; a mid-chain return repoints rather than clears; and a hop that lands the task back on the original sender's own board — by assign or by return — clears the chip entirely (their own pane must not say "Kevin has it" to Kevin). Note "return" always goes to whoever handed it to *you*, so the way home from a chain is an assign back to the sender.
- Pre-feature assignments were backfilled `accepted_at = updated_at` on the migrating boot, so nothing old retroactively appeared unanswered.

### Shared boards + the demo team (2026-08-20)
- **`users.share_board` (default 0) gates `GET .../users/:slug/shared-board`** — 403 until that person shares. With no auth this is a product rule, not a security boundary (any board is reachable by URL); it is the seam real permissions go in, and the server holds the line so the demo doesn't teach a habit the product wouldn't allow. `users.role` ("Accounting", "CTO") is display-only.
- **The team lives in the account popup** (click the user·project chip): a "Team boards" roster — avatar, name, role, greyed with "private" when unshared — plus "Share my board with the team" / "Make my board private" (`PUT .../users/:slug/share`). The header's job is to whisper; the team is a place you go occasionally.
- **A teammate's board opens as the team view** (`viewMode 'team'`, its own `#teamContainer`): banner (avatar, name, role, the sharing rule said out loud — plus "N things you sent are still unanswered" when true), person tabs for everyone shared, and seven day cards. **Read-only by construction, and deliberately not a mode of `renderBoard()`** — every board affordance is wrong on someone else's week, and a board with everything disabled reads as broken rather than as somebody else's; a smaller surface says what it is by shape. The route runs **no spillover and no calendar sync** (looking must never move anything), isn't project-filtered, and folds open past-due rows onto today in the response, not the data — except past calendar events, which are dropped (the owner's own prune only runs when *they* open their board, and a viewer must not see Monday's stale standup as Thursday's plan). Rows order with the position NULL-last idiom, matching the owner's own board. Awaiting rows there carry a flag: "Waiting on ⟨name⟩" if you sent it, "Sent by ⟨name⟩ · not accepted" otherwise. The project bar hides while it's open (`visibility: hidden` — it switches *your* boards); the view toggle becomes "back to your board".
- **`POST /api/companies/:subdomain/demo-team` seeds Margo (Accounting), Jay (Product Marketing), Yarwen (CTO) and Tessa (AI Assistant, `is_ai = 1`)** — each shared, with their own project board and a plausible seeded week. Idempotent two ways (existing teammate reused; week only seeded onto an empty board), because it's reachable from the account popup's "Add the demo team" row — which stays offered until all three exist (case-insensitively), since a board that already has other people must not hide it. **A pre-existing user with those names is only adopted if they look unused (zero tasks)** — a real Margo must not have her board force-shared and a demo role stamped on her by the seed button; "you can't see a board that wasn't shared" is the feature's one product rule.
- **`loadUsers()` runs at signup and session restore** and keeps `currentUser` pointed at the fresh row. It was defined-but-never-called before — after any reload, `allUsers` held only you, which silently emptied the assign popup and the roster.

### Task pages (/task/:id, 2026-08-21)
- **Every task has its own page** — `GET /task/:id` serves `public/task.html` (same one-static-file pattern as `/help`), which reads its id from the URL and talks to `/api/tasks/:id/page`. Like every board, reachable by anyone with the link: the app has no auth and the page inherits that honestly.
- **Three panes, in order: Background & instructions** (kept visually short — a brief, not a novel), **Notes**, and **Results**. Header carries owner · board · created day and an open/completed chip.
- **`tasks.background` and `tasks.results` live on the task row itself**, so when finished handed-over work moves home, the assignee's results ride back to the sender with it — no copying step, the move IS the delivery. The intended flow: Margo option-clicks her handover row, writes results on its page, ticks complete on the board; Kevin option-clicks the "done by Margo" row and reads what came of it. Board-only completion just leaves Results blank ("Completed on the board — no results were posted").
- **Notes are an append-only feed with attribution** (`task_notes`: task_id CASCADE, author_id SET NULL), never one shared blob — several people (later, agents) add to a task, and who-said-when is the half a shared textarea destroys. The composer sends `author_slug` from the browser's session; with no auth that is trust, not proof, and the nullable `author_id` says exactly that much. Links render as anchors; **image URLs render inline** (`renderRich()` in task.html: escape first, rebuild hrefs, `.png/.jpg/.jpeg/.gif/.webp` become `<img>`).
- **Access: Option+Click the task name** (board and List view; alt WITHOUT shift — Shift+Option is the quick-lock). Awaiting rows support it too via a dedicated listener (their description deliberately has no `data-task-id`), because the background is exactly what you read before accepting. Tooltips carry the gesture. Both editable panes autosave (debounce + blur) with a quiet state word — no Save button.
- **Gotcha fixed in review: SQLite's `CURRENT_TIMESTAMP` ("YYYY-MM-DD HH:MM:SS") is rejected by Safari's `new Date()`** — `dayLabel()` normalizes to ISO-with-Z before parsing or the created date renders raw on the one browser Kevin uses.
- **Postgres was considered and declined** (2026-08-21): the Railway volume already persists SQLite, this feature is two columns and one table, and a database swap would rewrite db.js for zero user-visible gain. Revisit only for multi-instance scaling or real concurrent write load.

### Locking tasks to a date (deadlines)
- A task can be **locked** to a date (a deadline that forces overdue work back to the present). Backed by the `tasks.locked` column; the lock date is just the task's `scheduled_date` while locked.
- **Lock gestures:** Shift+Option+Click the task body quick-locks it to its current day (with confirm); the 📅 icon on each pending task opens a popup to lock-to-this-day, pick a future date, or unlock. A locked task shows 🔒 and an amber left edge.
- Locked tasks are **exempt from auto-spillover**. A past-due locked task **pulls the calendar's first visible day back to its lock date** (anchor = min(today, earliest locked-incomplete date)); "today" stays highlighted by real date, and other overdue tasks still spill to today.
- **Overdue day panes get a red border.** When the anchor is pulled back, every day before today (`isOverdue: key < todayKey` in `generateDays()`, `.day-card.overdue` class) shows a 2px red (`#ef4444`) border + red header/date, so the first pane clearly reads as "not today"; today keeps its blue treatment. Gotcha: `selectedDayIndex` defaults to `0`, so the anchor-back overdue day is auto-selected — the red border must out-specify `.selected`'s blue border (`.day-card.overdue.selected` rule) while leaving the selection shadow intact.
- Moving a locked task forward (the → arrow) asks for confirmation; the lock follows to the new day. Assigning or returning a task clears the lock.
- **A locked task on its lock day renders its text red** (`.task-item.locked-today`, gated on `!completed && scheduled_date === todayKey`). Red overrides everything else on the row — including a series color/tint.
- **Project tabs never move.** All boards render into a single `#projectTabs` flex row in the user's own order; the active one is styled in place (`.active`) — tinted background + blue border in light, **white border** in dark (`body.dark .project-tab.active`), so the board you're on reads as lit against the slate bar. The old two-container split (`#projectTabs` = active, `#projectTabsOther` = the rest) is gone — it made the selected board jump to the front. Consequences that are load-bearing: every tab shares one geometry (3px/10px, 12px), `.due` compensates its 2px border with 2px/9px padding, and **`.active` carries no `font-weight`** — bolding the label widens that tab and nudges the rest of the row on every switch.
- **Renaming a board** lives in the same board popup as delete: clicking the tab you're already on now offers **Rename this board** above **Delete this board**. The row swaps the popup's name line for an inline field in place (`.rename-input`) rather than opening a modal — Enter commits, Escape cancels. `PUT /api/companies/:sub/users/:slug/projects/:id` takes `{ name }` and **regenerates the slug** (`projectSlugFrom()` in `server.js`, shared with create). Nothing in the app addresses a project by slug — there's no URL routing, and the session stores `project_id` — so a frozen slug would only drift from the name for no benefit; the one unused `/projects/:projectSlug/members` route is leftover from back-burnered collaboration. Two load-bearing details: the route **must stay declared after `PUT .../projects/order`**, because Express matches in declaration order and a `:projectId` above it swallows `order`; and `renameProject()` mutates the existing `projects` entry in place rather than replacing it, since `currentProject` is a reference into that array. Unlike delete and tab order, a rename is **company-wide** — every member sees the new name.
- **Deleting a board is per-user.** Clicking the tab you're *already on* opens a board popup (reuses `.team-popup`/`.lock-popup-menu`, same element as the account popup) with **Delete this board** — the click was a no-op before, so deletion costs no new affordance and stays one deliberate step off the main path. `DELETE /api/companies/:sub/users/:slug/projects/:id` drops the caller's `project_members` row and **their own** tasks (+subtasks) on that board; another member's copy is untouched. The `projects` row is destroyed only when the last member leaves. Two load-bearing details: `tasks.project_id` is `ON DELETE SET NULL`, so tasks **must** be deleted explicitly — letting the FK fire orphans them to `project_id = NULL` where no view can reach them and nothing can clean them up. And the route refuses to remove a user's **last** board (409), because zero projects is an empty state the app offers no way out of. No undo.
- **Tab order is per-user and drag-sortable.** `project_members.position` (NULL = never dragged) orders `GET /projects` via `ORDER BY CASE WHEN pm.position IS NULL THEN 1 ELSE 0 END, pm.position, p.created_at`, so the default is creation order and new projects append. `PUT /api/companies/:sub/users/:slug/projects/order` takes `{ project_ids }`, keeps only ids the user belongs to, dedupes, and appends any it wasn't sent — a partial or hostile list can't drop a board. Frontend: `attachProjectTabDrag()` + `reorderProjects()` splice the local array, repaint optimistically, then PUT. Order lives on `project_members`, not `projects`, so one member's arrangement never reorders anyone else's bar.
  - The tab drag and the series drag share the `dragstart`/`drop` events, so each gates on its own state var: tab handlers early-return unless `draggedProjectId` is set, task handlers on `draggedTaskId`. `justDraggedProject` (cleared on a 0ms timeout in `dragend`) swallows the click that can follow a drop on the origin tab, so dragging never switches boards. Desktop only — HTML5 DnD doesn't fire on iOS touch, same as the series drag.
- **Off-screen boards with a deadline flag their tab red.** `GET /projects` returns `due_today` per project (count of the user's `locked = 1 AND completed = 0 AND scheduled_date <= today` tasks — past-due locks count too). `renderProjectBar()` puts `.project-tab.other.due` (2px `#ef4444`, padding trimmed to 2px/9px so the tab doesn't grow) on any non-active tab with `due_today > 0`; the active tab never flags, since you're already looking at it. Counts refresh from inside `loadTasks()` via `refreshProjectDueFlags()`, which merges `due_today` into the existing `projects` array (never replaces it — that would drop the local `currentProject` reference) and repaints the bar. Every lock/complete/move/delete path already awaits `loadTasks()`, so the flag stays live with no extra call sites.
- **On the List (master) view, a locked task's date renders red** (`.project-task-date.locked-date`, bold). The master route SELECT must include `t.locked` for this — it's a hand-listed column list, not `t.*`, so new task flags the List view needs have to be added there explicitly.

### Series (task chains / dependencies)
- **User-facing copy says "next step in a series" — never parent/child.** The schema's `parent_task_id` naming is internal only; parent/child reads as hierarchy (task-contains-subtasks) where a series is a sequence. Help card + margin note were rewritten to step language 2026-08-05.
- **Drag a task onto another task** to make it the next step in a series: it splices in immediately after the drop target and moves to the target's day + 1 (`origin_date` untouched). Backed by `tasks.parent_task_id` (each task points at its predecessor; single successor enforced at link time, so a series is a linear linked list). `POST /api/tasks/:id/link`.
- **Countdown circles:** series members show a small number *inside the existing completion circle* — position-from-end over the whole chain, so the first step shows the series size and the last shows 1 ("steps remaining including this one"). Completing a member splices it out (see below), so the remaining chain renumbers on the next render. Empty circle = free-standing task. Day board only. Chosen over separate dots/badges after mocking 9 variants (`archive/pm-v*.html`).
- **Hover threads:** hovering any series member lights up the whole family (background tint), fades the rest of the board (`.board-container.threading`), and draws thin SVG bezier threads (`#chainOverlay`) between consecutive members across day cards. Hover-only, no pin — click still opens the subtask pane. Colors come from `CHAIN_COLORS` (violet/orange/fuchsia/indigo/cyan — no red, no green) keyed by root task id; color appears **only on hover**, the resting board stays monochrome.
- **Move cascade:** changing a series member's date (→ arrow, lock popup, any `PUT` with `scheduled_date`) shifts every later step by the same delta. The cascade **stops at the first locked step** (deadlines never drift; steps behind a lock compress the gap) and **skips completed steps** without stopping. Earlier steps never move.
- **Spillover cascades too:** an overdue series member spills to today and drags its successors forward by the same delta (same lock-stop rule), so a lagging series re-plans itself while keeping its spacing.
- **Boot chain repair:** `repairCompletedChainLinks()` in `server.js` runs on every boot and splices any completed task that still holds chain links (data from before completing-severs-links; re-fetches each row before splicing so consecutive completed members re-link their pending tail correctly). Idempotent; logs only when it fixes something.
- **Series never break:** assigning, deleting, or **completing** a member splices it out (successor re-links to predecessor) — `spliceOutOfChain()` in `server.js`. Completing severs one-way: reopening the task does NOT restore its links. Re-dropping a chained task repositions it (splice out, then insert). Frontend gotcha: `toggleComplete()` must `loadTasks()` when completing a chained task, because the splice rewrites *other* rows' `parent_task_id` server-side. Consequence: the countdown numbers renumber on completion now (the old "stable when a middle step completes" behavior is gone), and a 2-step chain dissolves entirely when either member completes.
- **Unlink:** hovering a chained task (day board only) reveals a ✂️ next to it whenever the task has a predecessor **and is pending** — the chain ROOT never shows scissors (it has no parent edge to cut); cut a 2-chain from its child. This is a recurring support question, not a bug. Clicking it (with a confirm) cuts just that one edge — `POST /api/tasks/:id/unlink` nulls the task's own `parent_task_id` and leaves its successors attached, so the task becomes the root of a new, separate series. Distinct from `spliceOutOfChain()` (used by assign/delete), which bypasses the task entirely by re-linking its successor straight to its predecessor.
- Frontend: `computeChains()` builds `chainInfo` (task id → chainId/countdown/color) from the loaded task list on every `renderBoard()`. After any date-changing call, the frontend re-fetches the full task list (`loadTasks()`) because cascades change other rows server-side.

### Day counter (days pushed forward)
- Each task stores `origin_date` — the day it was first **requested** for (capacity overflow counts as a push: origin = requested day, not the effective overflow day). It **never changes**: spillover, → moves, assign, and return all preserve it. Any new code that writes `scheduled_date` must leave `origin_date` alone.
- The day board shows a small light-grey **inclusive** day count after the task text (added Monday → "5" on Friday): days from origin to `max(scheduled_date, today)` + 1, hidden when it would read 1 (the origin day). Consequence: **the counter never displays "1"** — its first visible value is 2 (e.g. postponing a task to tomorrow immediately shows 2, both endpoints counted). The help page's postpone vignette shows "2" for exactly this reason. Rendered by `renderDayCounter()` in `index.html`; **day board only** — not the Main/master page. **Counts over 10 render red** (`.task-day-counter.lagging`) so lagging items get attention.
- Overdue **locked** tasks keep counting to today (they don't spill, but their age still climbs daily). **Completed** tasks freeze at the day they were completed.
- Tasks created before the migration backfill `origin_date = scheduled_date` on boot (their earlier push history was never recorded).

### Manual order (drag, or hover + 1-9)
Replaced the 1/2/3 priority marks on 2026-08-14. The exclamation marks are gone entirely; a task's rank is now just where it sits.
- **Drag a task to a row's top or bottom edge** to reorder it within its day — a solid blue line (`.task-item.insert-above/.insert-below`) shows where it will land. **Or hover a pending task and press `1`-`9`** to send it straight to that slot; `0` sends it to the bottom (a day holds 10, so ten single-key presses cover every slot).
- Backed by `tasks.position`, dense 0..n-1 within a day. **NULL means never positioned and sorts LAST** — which is what lets a newly created task append to the bottom of its day *without a single INSERT site knowing the column exists*. Don't "fix" this by assigning positions on insert; several INSERT paths (create, assign, return, `spawnNextRepeat`, calendar sync) would each have to be found and kept in step.
  - **The one deliberate exception is promote** (`placeTaskAfter()` in `server.js`), which has a specific slot to land in. It reuses the same ordering query as `PUT .../tasks/order` so the two can't disagree; any future "insert here" feature should call it rather than write `position` itself.
- **One gesture, two meanings, split by pointer position within the row** (`dropZone()`): the middle **40%** keeps the pre-existing series link, the top and bottom **30%** reorder. The series drag was there first and gets the forgiving centre target. Reordering is **same-day only** — across day cards the whole row means "series", so nothing that worked before changed.
- **`dragstart` must set `effectAllowed = 'all'`.** It was `'link'`, which is what a series drag is — but `effectAllowed` gates which `dropEffect`s the browser will honour, so leaving it silently suppresses *every* reorder drop with no error. `dropEffect` is then set per zone (`link` vs `move`), which also makes the cursor announce which drop you're about to get.
- Both gestures write through **one endpoint**, `PUT .../tasks/order`, so they can't disagree. The frontend splices its local array, repaints optimistically, then PUTs — same shape as `reorderProjects()`. Writes are chained per `date|project` (`orderWrites`).
- **The list re-sorts immediately now.** The old deferred `mouseleave` sort (`pendingPriorityRow`) existed because re-sorting slid the row out from under the cursor — but moving the row *is* the point here. Instead, a number press **holds** its task under the keyboard (`stickyTaskId`) until a real `mousemove`, so a quick "3 then 5" still targets the task you just moved. Re-rendering slides rows under a stationary cursor and fires `mouseover` but never `mousemove`, which is exactly why the hold survives.
- **The keydown branch must stay above the `viewMode !== 'calendar'` guard** (so it works on Main) **and above the type-to-focus fallback** — that fallback would otherwise swallow the digit into the add-task input. It early-returns when focus is in any `INPUT`/`TEXTAREA`/`SELECT`/contentEditable, so typing "3 eggs" never reorders.
- Hover detection reads the live CSS state via `document.querySelector('.task-item:hover, .project-task-item:hover')` — the row that visibly changed colour is exactly the row that moves.
- **Eligible rows:** pending only. Completed, assigned-away (`.forwarded`), placeholder and calendar rows are excluded — events are force-sorted to the top by `event_start`, so a position among them would never be read.
- Ordering is **display only** — it never writes `scheduled_date`, so it triggers no series cascade, no spillover change, and doesn't count against day capacity.
- **Migration:** the boot that adds the column backfills `position` from the *old* priority order (`priority DESC, created_at`) per (owner, project, day), so nobody's board reshuffles on deploy. One-shot — `ensureColumn()` now returns whether it actually added the column, and the seed hangs off that. `tasks.priority` is left in place, unread; `PUT /api/tasks/:id` still accepts it so older clients don't 400.

### Moving a task forward (the → arrow)
- Click → for **+1 day**, Shift+Click for **+1 week**, or **hover the arrow itself and press `1`-`9`** to jump that many days. Every one of those paths goes through **`moveTaskForwardDays(taskId, n, label)`** so the lock confirm and the "series follows" notice can't drift apart between them.
- **The arrow lives inside the row, so hovering it matches both hit-tests.** `hoveredForwardArrow()` is therefore checked **before** `hoveredTaskRow()` in the digit branch — the more specific target wins. Same digit, two meanings, split by what the pointer is actually on: over the row it's a slot, over the arrow it's days.
- **`0` over the arrow is swallowed, not passed through.** "Forward nothing" is meaningless, and letting it fall through would reorder a row the pointer isn't sitting on.
- **`stickyArrowTaskId` holds the arrow under the keyboard** exactly like `stickyTaskId` holds a row — a move slides the arrow to another day card, so a follow-up digit would otherwise land on whatever took its place. One `mousemove` listener clears both. Consequence: `3` then `2` is +5, not +2.
- **The move optimistically writes `task.scheduled_date` locally before the PUT.** `moveTaskToDate()` is async and nothing else updates the row until `loadTasks()` returns, so without this a fast second digit would compute its hop from the stale date and lose the first one.

### Repeating tasks (hover + `r`)
- **Hover a pending task and press `r`** to cycle `off → daily → weekly → monthly → off`. Backed by `tasks.repeat_rule` (NULL / `'daily'` / `'weekly'` / `'monthly'`, validated against `REPEAT_RULES` server-side). A repeating row shows a quiet grey `↻d` / `↻w` / `↻m` glyph. **Deliberately no popup** — a cadence picker is the rabbit hole the app exists to avoid, and three cadences cover the mortgage and the toothbrush. Sub-daily, arbitrary intervals ("every 3 weeks"), weekday-only and "on the 1st" are all out of scope precisely because adding them forces a dialog back into existence.
- **Only ever ONE instance exists, and completing it is what creates the next** (`spawnNextRepeat()` in `server.js`, called from `PUT /api/tasks/:id` after `spliceOutOfChain`). There is no scheduler and nothing is materialized ahead — the alternative (pre-creating 30 days of instances) would put a "brush teeth" row on every day card and eat the 10/day capacity. Miss an occurrence and nothing piles up: the single instance just spills forward like any other task, which is already the app's whole thesis.
- The next date is measured from **the completed instance's own `scheduled_date`, not today**, so a rhythm doesn't drift when you tick something late. `addMonths()` clamps end-of-month — Jan 31 + 1 month is **Feb 28**, not Mar 3; `setUTCMonth` alone overflows into the following month.
- The new instance inherits `description`, `project_id`, `locked`, `priority` and the rule, and goes through `findDayWithCapacity()` so a repeat can't blow the 10/day cap. It carries **no `parent_task_id`** — the completing task has already been spliced out of any series, and a fresh instance is free-standing. It gets its own `origin_date` (each occurrence starts its own count).
- **Locked + repeating is the intended combination** for a bill: the next instance inherits `locked = 1` at its new date, so red project-tab flagging and board anchoring work for recurring deadlines for free.
- **The repeat glyph replaces the day counter** (`renderDayCounter()` early-returns on `repeat_rule`). A daily habit would otherwise show a permanent red "14", which reads as a bug rather than a nag. `paintDayCounter()` removes it live when `r` is pressed, so it doesn't linger until the next full render.
- **Refused on calendar rows** (`task.source !== 'calendar'` guard in `PUT`, same shape as the `locked` refusal) — an imported event is already regenerated by the feed, so a second regeneration source would duplicate it every time you ticked one. **Cleared by assign and return**, alongside `locked`.
- Frontend gotchas: `setRepeat()` shares the `priorityWrites` chain with `setPriority()` (both PUT the same task, so one chain per id keeps a fast `r`-then-`2` from landing out of order). The `r` keydown branch sits **immediately beside the priority branch** — above the `viewMode !== 'calendar'` guard and above the type-to-focus fallback, which would otherwise swallow the "r" into the add-task input; the same `INPUT/TEXTAREA/SELECT`/contentEditable guard keeps typing "return the drill" from setting a repeat. `hoveredPriorityRow()` was renamed **`hoveredTaskRow()`** now that two features share it. And `toggleComplete()` must `loadTasks()` when completing a repeating task — the next instance is created server-side and would otherwise stay invisible until reload (same reason chained tasks refetch).
- Unlike priority, a repeat doesn't affect ordering, so there is **no deferred re-sort** — the glyph just paints in place.

### Calendar import (📅 toggle)
- A **📅 Calendar switch** sits beside the 🧠 assistant switch. Connecting a calendar subscribes to its **secret iCal (ICS) feed URL** and mirrors the next **14 days** of timed events onto the board as ordinary task rows with `source = 'calendar'`.
- **Why a feed URL, not OAuth:** Google, Proton, iCloud and Outlook all publish a secret iCal address; Proton has no API at all; and the app has no auth story to hang OAuth tokens on. One code path covers every provider. Backed by `node-ical` — **the dependency list is four now, not three** ("express, cors, sql.js — that's it" is out of date). It earns its place by expanding RRULE, EXDATE and per-instance `RECURRENCE-ID` overrides; hand-rolling recurrence means a real calendar shows its standup once and never again.
- **Imported rows are deliberately NOT locked, and this is the whole design.** An earlier draft locked them to buy spillover exemption. But `locked` is what drives board anchoring (`computeAnchorKey`), red project tabs (`due_today`), red task text (`.locked-today`) and the amber edge — four behaviors that would each misfire *every day* on an event. Leaving `locked = 0` eliminates all four for free. Day capacity is also free: calendar rows carry `project_id = NULL`, which `findDayWithCapacity` buckets separately, so events never eat a project's 10/day.
- **One guard replaces all of them: calendar rows are excluded from spillover**, at *both* sites where `locked` is already checked in `GET .../tasks` — the overdue SELECT and the fixed-point loop's freshness re-check. This single check is load-bearing: miss it and yesterday's standup lands on today and repeats daily, forever. Setting `locked` on a calendar row is additionally refused by `PUT /api/tasks/:id` and by the Shift+Option+Click quick-lock, so the UI is not the only thing holding it.
- **`project_id = NULL` is deliberate**, and is what makes one row show on every board (your 2pm dentist appointment constrains whatever board you're looking at). The tasks route widens its filter to `(t.project_id = ? OR t.source = 'calendar')`. This is the one place a NULL `project_id` is meaningful — the "orphan" warning elsewhere in this file does not apply, and a cleanup that sweeps NULL project_ids would delete every imported event.
- **Past events are pruned, not spilled** — a meeting happened whether or not you ticked it. Consequence: an un-completed event leaves no trace, and any subtasks built on it are cascade-deleted with it. The prune runs **unconditionally**, including when the fetch fails, because it needs no network knowledge.
- **A failed fetch never reconciles.** Treating a 404 (the user regenerated their secret address) as "the calendar is empty" would wipe the board. Failures record `last_status`/`last_error` on the feed and are surfaced in the connect popup.
- **Events are matched on `external_uid` and updated in place, never deleted-and-recreated.** Subtasks `CASCADE` on task delete, so recreating would silently destroy a subtask pane the user built on an event. `completed` is never touched either, so completing an event sticks.
- `external_uid` is `UID + '#' + dateKey`, because **every instance of a recurring event shares one UID**.
- **Rendering:** `.task-item.calendar` gets a passive 📅 origin marker and a grey `event_start` time chip, and sorts **above everything else** (`sortByPosition` keys on calendar first, ties broken by time). Withheld on event rows: the → arrow, drag-to-series, the 📅 lock popup, delete, and the 1-9 ordering keys — each would be silently reverted by the next sync. Kept: the completion circle and the subtask pane.
- **Sync is lazy and fire-and-forget** from `GET .../tasks` on a 15-minute throttle, with an in-flight guard. There is still no scheduler in this server. **Gotcha:** `syncFeed` must call `flushDb()` itself — the per-request `res.on('finish', flushDb)` has already fired by the time a background sync finishes, so its writes would set `dirty` with nothing scheduled to persist them. Same pattern as `repairCompletedChainLinks()`.
- **Timezone:** day keys are UTC-anchored labels, but events carry local times — an 8pm PDT event is the next day in UTC and would land on the wrong card. The browser's IANA zone is stored on `calendar_feeds.timezone` and day keys are derived with `toLocaleDateString('en-CA', { timeZone })`. **`node-ical` already re-anchors recurrences across DST** (verified both directions: a 9:00 standup stays 9:00 in PST and PDT) — do **not** add an offset correction on top, which double-shifts every recurring event by an hour.
- **Filtering ("ignore holidays, etc."):** drop all-day events, anything marked free/`TRANSP:TRANSPARENT` (how Google tags holidays and birthdays), `X-MICROSOFT-CDO-BUSYSTATUS:FREE`, and `STATUS:CANCELLED`.
- **Calendar import is labelled Beta**, in the help page (a `.beta-badge` chip on the card heading, `.card.beta` amber treatment, `.beta-note` for the unsettled bits) and in the app's 📅 popup title (`.beta-tag`). The badge is **amber**, not red or blue — it borrows the lock state's "held, not settled" reading rather than the overdue red or ordinary-UI blue. The privacy story is deliberately left open in the copy ("still being figured out"): the honest position today is no password + event titles readable by anyone with the board link + the feed URL stored server-side, so the card tells users to point it at a spare calendar rather than pretending the question is answered.
- **Calendar has its own help section, not a card in "More fun" (2026-08-17)** — `<h2>Add calendar events</h2>` with a `.beta-badge`, sitting after Subtasks and before Run your own copy. Three cards for one feature outweighed everything around them in a section of one-card features, and setup instructions are reference material, not a tour stop. The badge moved to the `h2`; the overview card's `h3` dropped its own so Beta isn't stamped twice in 40px. The card keeps its `.card.beta` amber treatment.
- **Three help cards cover calendar setup**: the overview (with the demo and margin note), **Finding your calendar link** (Google / iCloud / Outlook menu paths), and **Proton Calendar**, which carries a `Paid plan` badge — Proton's share link is a paid feature and Proton publishes no API, so free-plan users have no way in at all. That is a support question waiting to happen, not a bug.
- `docs/animation/build.js` **strips `.beta-badge` spans out of a scene's title** before slugifying; without it the badge text lands in the filename (`12-bring-in-your-calendar-beta.html`) and the contact-sheet tile.
- **The feed URL is a bearer credential** for the whole calendar. Stored server-side, returned only masked, never in localStorage. Since the app has no auth, enabling this publishes event titles to anyone who knows the team + user name — the connect popup says so in one line. The fetch is also an SSRF surface: https only, private/loopback/link-local hosts rejected, 10s timeout, 5 MB cap, 500-event cap.
- Calendar rows are **absent from the List/master view** (it filters `t.project_id = ?`). That is intended — List is about project work.

### Hyperlink tasks
- Any URL inside a task's text renders as a clickable link (`.task-link`) that **opens in a new tab** (`target="_blank" rel="noopener noreferrer"`). Day board **and** the Main/master page, plus subtask rows (so AI-generated links are clickable); forwarded/placeholder rows are still plain text.
- `linkifyText()` in `index.html` escapes the whole description first, then wraps matches of `TASK_URL_RE` (`http(s)://…` and `www.…` **only** — so a `javascript:` string can never become an href). Trailing sentence punctuation (`. , ) ] ' "`) is trimmed back out of the link. `www.` forms get an `https://` prefix on the href.
- Task descriptions are therefore **HTML-escaped now** (they used to be injected raw — that was an XSS hole). Typed markup shows literally.
- Links carry `draggable="false"` so dragging from the link body still starts the task's series drag instead of a URL drag.
- Both description click handlers (board + master) early-return on `e.target.closest('a.task-link')`: a link click navigates and does **not** toggle the subtask pane. Clicking any non-link part of the text opens the pane as before.
- **URLs in subtask rows render as a link glyph, not as text** (`linkifySubtask()`; board rows keep `linkifyText()`, since those URLs are typed by the user to be read). The glyph sits **where the URL was**, so a trailing citation lands at the end while a mid-sentence link keeps its grammar; hover shows the **domain** — a query-string path is unreadable at 10px and isn't what the user is deciding on. Wrapping parens are eaten with the URL (else a stripped citation leaves `()`), surrounding whitespace is not.
  - **`SUBTASK_URL_RE` matches bare domains, which `TASK_URL_RE` never did** — and that was a silent gap: the model writes `homedepot.com/s/cedar`, so AI links were costing the width of a URL *while not even being clickable*. The bare form is admitted only against an explicit TLD allowlist (`SUBTASK_TLDS`), which is what keeps `$4.28` and `1.5in` out, and the href is always rebuilt with an `https://` scheme, so a `javascript:` string still can't become one.
- **Completing any task closes its subtask pane** (`toggleComplete()` drops it from `expandedTaskIds` on `willComplete`; both views share this handler). Originally this was gated to tasks whose text contained a URL — the gate (and the `taskHasLink()` helper) was removed 2026-08-05. Reopening a completed task leaves the pane closed.

### Quick lists ("list …" tasks)
- A task whose description starts with the word **"list"** (`/^list\b/i` — `isListTask()` frontend, same regex in `server.js` and `ai.js`; `\b` keeps "listen…" out) gets a different subtask pane: the user's **quick list on top, AI "Suggestions" below**.
- **A list pane has no rail and no headings (2026-08-16).** The user's items are `assignee_type 'human'`, rendered as **checkbox + text**; suggestions are **↑ + text**, and that difference — plus a dashed divider (`.list-suggestions`) — is the *only* thing separating the two halves. "My list" only repeated a task already called "list stuff for taco night", and "Suggestions" was already said by the ↑ that no list row carries; two headings cost two lines of a 178px pane and bought nothing. The assignee emoji is gone too: every suggestion is the AI's, so saying so on each row is noise.
- Below the user's items, dashed **blank slots** (`.quick-slot`): 3 to start, then always exactly one — `Math.max(3 - count, 1)`. Enter creates the subtask and refocuses the next empty slot (`addQuickListItem()`), so items can be rattled off.
- **Suggestions**: AI-generated rows are forced to `assignee_type 'ai'` server-side. Clicking ↑ PUTs `assignee_type: 'human'` — the row moves into the list and survives regeneration. **↺ replaces every suggestion the user hasn't adopted** and leaves the adopted ones alone, which is exactly what "regenerate" should mean here.
- **List panes build their own rows and never call `subtaskRow()`** — so a list row can't grow a promote arrow, a 🔎, or an assignee emoji by accident. This also retired the `moveUp` parameter and its `pending.map(subtaskRow)` trap (map's index used to land in `moveUp`); the builder now takes one argument and `pending.map(subtaskRow)` is safe.
- **If a "list" task shows the ordinary subtask pane, check the wording:** `isListTask()` is `/^list\b/i`, so the description has to *start* with "list". "list stuff for taco night" gets the list pane; "taco night list" gets a normal pane — whose ↑ promotes to the board, which reads exactly like a list bug.
- **Regenerating a list task deletes only the AI rows** (`DELETE … WHERE assignee_type='ai'`) and the endpoint returns the **full** subtask set (the frontend replaces its cache with the response — returning only created rows would vanish the user's items from the UI).
- `ai.js` `buildPrompt()` branches on the same regex: list tasks ask for **7 concrete candidate items** (real titles/places/products, links where useful) returned as bare JSON strings; the parser accepts strings or `{description}` objects. `generateMockSubtasks` has a matching placeholder branch.
- History: v1 of this feature (same day) rendered suggestions as a Family Feud board — hidden ranked slats, reveal-on-match, adopt-on-click. Kevin cut the game for the plain split pane within hours. Lesson: playful mechanics layered on a simple feature are the first thing he trims; ship the minimal interaction first.

### Master Project Page
- Each username has a **master project page** that lists all their projects. (The UI button for it is labeled **"List"** — renamed from "Main" 2026-08-05; internally the view mode and API route are still `master`.)

## Architecture

- All frontend state loads from API on signup, no local persistence
- Tasks have an owner (whose board they're on) and optional assigned_by (who gave it)
- **There is no `assigned_to` column on `tasks`, and assignment is not a flag.** `POST /tasks/:id/assign` rewrites `owner_id` outright — the row *moves* to the other person's board. So any query already filtered by `owner_id` has excluded assigned-away tasks for free, and adding an `assigned_to IS NULL` clause is both wrong and a 500 (`no such column`). The frontend's `task.assigned_to_id` is a **client-side optimistic field only**, set by `assignTaskToMember()` so the row can render as forwarded until the next load; it never comes back from the API.
- Companies use subdomain-based URLs: `{subdomain}.movealong.com/{user_slug}`
- Database auto-creates on first run; writes mark it dirty and it persists **once per HTTP request** (`flushDb` on response finish, plus SIGTERM/SIGINT) via an atomic tmp-file + rename in `saveDb()` — not per statement

## API Pattern

All endpoints under `/api`. RESTful. JSON in/out.
- Companies: `POST /api/companies` (**sign in *or* sign up** — an existing team + user name returns that account with `returning: true` instead of 409ing; a known name is the credential, since there's no auth), `GET /api/companies/:subdomain`
- Users: `GET|POST /api/companies/:subdomain/users`
- Tasks: `GET|POST /api/companies/:subdomain/users/:slug/tasks`
- Task actions: `PUT /api/tasks/:id`, `POST /api/tasks/:id/assign`, `POST /api/tasks/:id/return`, `DELETE /api/tasks/:id`

Full endpoint reference lives in `reference/api-reference.md`. Schema lives in `reference/data-model.md`. Check those before re-deriving from code.

## Deployment

- **GitHub:** [kevintraywick/movealong](https://github.com/kevintraywick/movealong), default branch `main`. No PR/commit conventions formalized yet.
- **Railway:** Auto-deploy on push to `main`. Build/start uses `npm start` (which runs `node src/server.js` from `server/`).
- **`engines.node` in `server/package.json` is what Railway uses to pick a Node version, and it picks the MINIMUM the range allows.** `">=18"` got Node 18.20.8 — which took production down the first time calendar import deployed: `node-ical` uses the RegExp `v` flag (`"gv"`), Node 20+, at module load, so `require('./calendar')` threw `SyntaxError` before the server ever listened. A 502 crash loop, invisible locally on Node 23. It is now `">=22"` (node-ical's own floor). **Bump it whenever a dependency raises its engine requirement** — a local `npm install` will never catch this.
- **`require('./calendar')` is wrapped in try/catch in `server.js`**, falling back to a no-op stub (`maybeSyncInBackground` no-ops, `getFeed` returns null, the rest throw a clean "unavailable"). Calendar import is optional and is the only third-party parser in the server; a module that won't load should cost you the calendar, not the whole board. `railway logs --deployment` is what surfaced the original crash — reach for it before guessing.
- **Env vars in Railway:** set `ANTHROPIC_API_KEY` for real AI subtask generation. It is **not** required to boot — without it the server runs and falls back to mock subtasks (see Environment Variables). **Set `AI_ACCESS_KEY` alongside it** so only the owner's browsers (key entered via Shift+Click on 🧠) trigger billed calls.
- **Database persistence:** No volume attached. `server/movealong.db` lives on the ephemeral container filesystem, so every deploy wipes all data. Attach a Railway volume (e.g. mount at `/data`) and set `DB_PATH=/data/movealong.db` before this is usable for real users.
- **Custom domain:** Not configured. The `*.movealong.com` subdomain pattern in the code is aspirational until DNS + a proxy are set up.

## Key Design Decisions

- No authentication yet (URL-based access, auth is a planned next step)
- Frontend is a single HTML file with inline CSS and JS
- sql.js chosen to avoid native compilation issues
- 30-day calendar view with horizontal scroll
- Incomplete past tasks spill over to today automatically — **except locked tasks**, which stay pinned to their date
- **Day keys are UTC-anchored labels, but *which* label is today is a local question.** `YYYY-MM-DD` keys and all arithmetic on them (`addDays`, `addMonths`, `generateDays`) stay UTC-anchored — that part is right and must stay that way. What was wrong until 2026-08-14 was deriving today from `new Date().toISOString()` on both ends: at 9pm CST the board already read Saturday, because it was Saturday in UTC. Six hours of every day showed the wrong "today", and spillover moved tasks early to match.
  - **Frontend:** `getTodayKey()` is `new Date().toLocaleDateString('en-CA')` — `en-CA` formats as `YYYY-MM-DD`, which is exactly the key format, so nothing needs reassembling. `getTomorrowKey()` builds off that key, not off the clock.
  - **Backend:** every request-scoped "what is today" goes through **`todayKeyFor(req)`**, which reads an **`x-tz` header** (the browser's IANA zone, sent by `api()` on every call) and formats through `Intl`. Unknown or absent zone falls back to UTC — so curl, old clients and background work behave exactly as before. There is no schema change and nothing is cached: a laptop that crosses a timezone follows on the next request.
  - Sites that must use it: spillover (`GET .../tasks`), `due_today` on `GET .../projects`, subtask return, and the calendar sync's `todayKey`. Any new "today" on the server belongs there too — a second UTC-derived today would reintroduce exactly this bug in one corner.
  - Not covered on purpose: `monthKey()` for the AI budget is still UTC. A budget month boundary being a few hours off costs nothing, and per-user month math would have to survive users moving.
- Day cards are **200px** wide (shrunk from 400px). The subtask pane hangs absolutely below its day column at `width: 100%` — **never wider than the day it's attached to**
- **The board clips vertically, and the subtask pane lives inside that clip.** `.board-container` sets `overflow-x: auto`; CSS then computes `overflow-y` to `auto` as well (one axis can't scroll while the other stays visible), so the container is a scroll box that cuts off anything hanging below it — and `.subtask-pane.board-pane` is absolutely positioned at `top: calc(100% + 10px)` under its day column. `padding-bottom` on `.board-container.has-expanded` is what buys the pane room. It was a flat **440px**, which guillotined any taller pane mid-row (a 7-step pane runs ~640px, so it lost ~230px); `scrollbar-width: none` hid the scrollbar, so it read as a hard wall rather than something scrollable. **`fitExpandedPane()` now measures the open pane and sets `padding-bottom` inline** — columns are `align-items: flex-start`, so every column shares a top edge and `pane.offsetTop + pane.offsetHeight` is directly comparable to the tallest column's height. It runs at the end of `renderBoard()`, and every path that changes pane height (async subtask load, quick-list add) already re-renders through `renderView()`. The 440px CSS value is kept only as a pre-measurement fallback. **Any new absolutely-positioned board child has the same problem** — reserve for it in `fitExpandedPane()` rather than adding another constant.
- Subtask pane: a single contained card listing up to 7 AI steps (plus user-added ones) as compact rows, ↺ "Regenerate all steps" absolutely positioned top-right. **Controls live in a narrow vertical left rail (`.subtask-rail`, 18px) — check · assignee emoji · ↑ promote · ↻ re-research, stacked — with the step text beside it** (redesigned 2026-08-16 from mockups `archive/st-v1..v4.html`; v2's horizontal strip shipped first, then the rail replaced it same day). A day column is 200px, so the pane has ~178px of usable width; the old inline row spent ~60px of it on controls, and the horizontal strip that briefly replaced it spent a whole *line* per row instead. The rail costs ~24px of width and no line at all, and the icons line up down the pane rather than restarting at every row. **The trade is height on rows carrying all four icons** — the rail is then taller than two lines of text; if that ever bites, the fallback is a 2×2 rail, not a return to the strip. Not one-card-per-subtask. Dependent subtasks indented under parents. **Completed subtasks disappear from the pane** (filtered at render; the server keeps them for the List view's n/m progress count) — there is currently no way to un-check one from the UI. "list …" tasks render the quick-list variant instead (see Quick lists above)
- **The → arrow is gone (2026-08-16), replaced on the strip by ↻ "Research this step again".** The → said "Send to AI agent" while its handler re-researched the row — a control whose label and job disagree. ↻ says what it does and still calls `researchSubtask()` / `POST /api/subtasks/:id/research`. It is shown **only on rows research has already been through** (`st.researched`): an unresearched row is covered by the pane's "Research these steps" button, and offering both would be two controls for one job. Styled quieter than ↑ (no fill until hover) because it spends money, and it **spins while its research runs** (`.subtask-item.provisional .subtask-rerun`) — research takes 15-60s and nothing else on the row changes in the meantime, so without the spin the click reads as having done nothing. `researchSubtask()` adds `.provisional` synchronously on click, so the feedback is instant rather than waiting on the 202. Real dispatch-to-an-agent is still unbuilt. ↑ keeps its list-pane meaning ("move to my list") and is unaffected.
- **Clicking the assignee emoji still opens the assign popup.** Collapsing "send to an agent" into that click was considered and declined — assignment is its own gesture, and overloading it would decide the agent-dispatch model as a side effect of a layout change.
- **Single-pane rule:** only one subtask pane may be open at a time. Every site that adds to `expandedTaskIds` must `clear()` it first (board + master click handlers, both auto-expand-on-add paths). Same-day board panes are absolutely positioned at identical coordinates, so two open at once silently occlude each other — this was a real bug
- **One type scale, 13px base.** `body` is 13px and every component sits on ~11/12/13/14/15px (day headers 14, section names 15, labels 11-12). The old split — 22px base with a 13px board inside it — is gone; don't reintroduce outsized text on the Main page, header, or modals. The only exception is the wordmark.
- **Favicon:** a white chevron on the accent blue (`#0ea5e9`) — the same forward arrow that moves a task to the next day, chosen because it's the one gesture the product is about and a single shape is all that survives 16px in a tab. The chevron is **oversized and bleeds off all three ends**: drawn to fit inside the tile it was a thin stroke on a mostly-blue square and read as a media "next" button, where bleeding makes white half the mark. **Safari pinned tabs ignore the favicon entirely** and use `rel="mask-icon"` — a single-colour silhouette Safari tints itself (`favicon-mask.svg`, emitted by the same builder). Without one, a pinned tab shows a letter derived from the **domain**, not the page title. Ship it; it costs nothing.
- **A letter tile is a Safari-side caching problem, not a markup problem — don't go changing the icon tags for it.** Chasing a grey "R" here burned several wrong diagnoses: an empty favicon-cache directory, then a pinned-tab/mask-icon theory on a user who doesn't pin tabs. Verified facts: all five icon files serve with correct MIME types; `index.html` and `help.html` carry **byte-identical** icon links; the chevron renders in Chrome, in a freshly-typed Safari tab, and on `/help` — yet Safari still showed a letter on `/` and in a saved bookmark. That is Safari holding an icon it cached when the site genuinely had none (the favicon shipped hours after the site went up, during a crash loop). Its cache lives in a TCC-protected container the shell cannot read, and bookmark icons survive deleting and re-adding the bookmark.
  - **One-step diagnostic before touching any code: open a brand-new tab and paste the URL in directly.** If the icon appears there, the markup is fine and the rest is cache.
  - The `rel="icon"` order (SVG first, PNGs after) was suspected twice and cleared twice — `/help` works with exactly the same order. Leave it alone. The mask drops the tile (a silhouette of a filled square pins as a blob) and pulls the chevron back inside the canvas (the bleed only reads against the tile it cuts into). Picked from eight variants judged at 16px (`archive/favicon-variants/build.js`, gitignored — rerun it to explore more). **Gotcha:** the bleed means the chevron must be clipped to the rounded square. The rasterizer gets that free from the tile's alpha channel, but `svg()` needs an explicit `clipPath` — without it the SVG grows spikes past the corners that no PNG shows, so verify the SVG separately (`qlmanage -t -s 192 -o <dir> favicon.svg` renders it through WebKit, the same engine Safari uses). `node docs/favicon/build.js` regenerates the whole set (`favicon.svg`, `favicon-32.png`, `favicon-192.png`, `apple-touch-icon.png`, `favicon.ico`) into `server/public/`, where express.static serves them; both `index.html` and `help.html` carry the link tags. The generator defines the shapes as signed distance functions and supersamples 4x4, and hand-rolls the PNG/ICO encoders on `zlib` — **no image dependency, and don't add one**. Edit the geometry constants at the top of the script and rerun; never hand-edit the binaries. Check any change at 16px (the script's math is easy to render as ASCII) — the mark is designed for the tab, not the file listing.
- **Wordmark:** "Move<span>Along</span>" in self-hosted Bricolage Grotesque 800 (`public/fonts/bricolage-grotesque-800.woff2`, ~38 KB, served by the express.static middleware) at 17px — small but heavy, "Along" in accent blue. It is the only non-system type in the app; don't use the display face anywhere else.
- **Quiet single-row header:** 44px min-height, blur/white bar with bottom border, full-bleed via negative margins against `body`'s 20px padding. **It is `position: sticky; top: 0; z-index: 90` (2026-08-16)** — an open subtask pane can run 600px+ tall, and scrolling to read step 6 used to take the board switcher, the AI switches and the help badge off-screen with it. 90 sits above the board and its panes but below every popup (100) and modal (1000+), so nothing that opens *over* the header lands behind it. Everything in the chrome whispers (grey, 12-13px) — nothing outranks a day header. **The bar reads as four groups and is spaced to say so (2026-08-16):** wordmark + `+` · boards · the three switches · view/theme/account/help. **Three `auto` margins split the free space three ways** — `#projectTabs { margin-left: auto }`, `#assistantSwitch { margin-left: auto }`, `#calendarSwitch { margin-right: auto }` — so the boards and the switches sit toward the middle with room on both sides, instead of being pinned against the wordmark and the view toggle. Then `.assistant-switch + .assistant-switch { margin-left: -6px }` pulls the three into an 8px cluster against the header's 14px gap — so the boundaries read louder than the items inside a group. Order: wordmark · + new project (**glyph only since 2026-08-16** — the words were the loudest thing in a bar whose job is to whisper, and `title`/`aria-label` carry the meaning; 18px so a bare `+` doesn't disappear, blue, **no resting ring** — a permanent circle would be a second bordered control beside the wordmark and read as clutter, so the hover *is* the circle) · tabs (all projects in user order, active styled in place; `#projectTabs` carries one of the three `auto` margins) · 🧠 · 🔎 · 📅 switches (**🧠 carries the `margin-left: auto`** that splits left/right — it moved here from the old segmented view toggle). **Icon-only since 2026-08-16** — "Assistant", "Research" and "Calendar" were three of the longest strings in a bar whose job is to whisper, and each switch already had a `title`. Because the words are gone, **the titles now carry the hidden gestures**: Shift+Click on 🧠 (AI access key) and on 🔎 (budget, alongside the live spend). **The pill is gone and the icon IS the switch (2026-08-17).** A control that is already `#cbd5e1` when off and `#0ea5e9` when on does not need a second object beside it saying the same thing; deleting the three pills took three objects out of the bar and cost nothing. The switches now use exactly the `.focus-toggle` vocabulary — grey off, the wordmark's blue on, `#475569`/`#38bdf8` in dark, no background in any state.
  - **The icons stayed emoji.** A stroked-SVG set was built and reverted the same day: the switches are 🧠 🔎 📅 at **16px** (matching the stroked ghost/view/theme icons beside them), **`grayscale(1)` + `opacity: .45` when off**, their own colour when on. This works here and specifically *not* for the focus ghost — 👻 is a white emoji, so desaturating it leaves nothing on a white bar, whereas these three each have real colour to lose. **Tinting an emoji blue was tried and does not work**: a filter can only rotate the hues already present, so `sepia+hue-rotate` yields a glossy multi-tone blue object (the calendar keeps a white "JUL 17" on a solid blue block), and the constants are tuned to Apple's artwork alone.   - **The focused day is the one the user picked, else today.** `selectedDayIndex` alone is wrong: it defaults to `0`, and day 0 is the *anchor*, which gets pulled back to a past-due lock date whenever one exists — so an unpicked board would focus an overdue day. A `hasPickedDay` flag (set in `selectDay()`, which every click and arrow key goes through) decides between the two.
  - **Dimmed, never hidden, and never `pointer-events: none`.** Clicking a dimmed day is how focus moves to it, and a day that vanished would take the shape of the month with it.
  - **A series outranks the dimming, two ways.** Opening the subtask pane of a chained task lights every day that chain touches (`focusedDayKeys()` walks `chainInfo` for the expanded ids); hovering any member lights its members' day cards live (`.day-card.chain-lit`, added in `drawChainThread()`, cleared in `clearChainThread()`). A chain half-faded across days reads as broken rather than quiet.
  - `focusedDayKeys()` must be called **after `computeChains()`** in `renderBoard()` — the chain's days are part of its answer.
  - **Outline only, no filled pill, in either state** (grey `#cbd5e1` off, the wordmark's `#0ea5e9` on). The tinted background every other toggle gets is fine behind a thin grey glyph, but behind an already-bright blue one it stacks brightness on brightness and makes a *view preference* the loudest thing in the bar. Using the wordmark's own blue also keeps the header at one blue instead of two.
  - **The icon is an inline SVG, not the 👻 emoji, and that was a bug first.** 👻 is a *white* emoji: greying it for the off state (`filter: grayscale(1)` + `opacity: 0.45`) rendered it invisible against the header's white bar — fine in dark mode, gone in light. Any "grey it out" treatment of an emoji has this trap; stroke chrome icons in `currentColor` (as the view toggle already does) so both states are a real colour.
- **Chain hint chip:** a dashed dismissible whisper ("Drag a task onto another…") renders in today's card when the board has 2+ pending tasks and no series exists (`shouldShowChainHint()`). `localStorage['movealong.hint.chain']` stores a session-appearance count (incremented once per session) — the chip retires after **3 sessions**, on dismiss (`'dismissed'`), or the moment a chain exists.
- Accent color is a **sky-blue ramp** (`#38bdf8` bright / `#0ea5e9` fills / `#0284c7` dark hover), tints `#f0f9ff`/`#bae6fd`. Replaced the old emerald green — use blue for any new UI, not green. **Red (`#ef4444`) is reserved for semantic warning/overdue signals** (e.g. overdue day panes), not decoration — it's the one sanctioned exception to blue-only
- AI agents do research and analysis after initial subtask generation so user gets immediate feedback first
- Day capacity: max 10 pending tasks per (owner, project) per day. New tasks created on a saturated day overflow to the next day with capacity (creation-only; assign/return/move are not capped)
- **AI assistant master switch** (🧠 toggle, `localStorage` `movealong.assistant`, default on): when on, adding a task auto-generates subtasks and opens the pane; when off, the task is created bare with no AI call
  - **Shift+Click the 🧠 toggle** prompts for the **AI access key** (`localStorage` `movealong.aikey`, sent as `x-ai-key` on every `api()` call). When the server sets `AI_ACCESS_KEY`, only requests with the matching header get real AI (`aiKeyAllows()`, timing-safe compare); all others silently get mock subtasks. Unset server-side = open (rate-limited) AI as before. Second layer: per-IP hourly + global daily caps (`AI_LIMIT_PER_IP_HOUR`/`AI_LIMIT_GLOBAL_DAY`).
  - **Known gap:** the toggle only gates `addTask`/`addTaskFromMaster` (task creation). Expanding an existing task's row just re-reads stored subtasks (`GET /tasks/:id/subtasks`, no AI call either way). But the ↺ "Regenerate steps" button (`regenerateSubtasks()`) calls `POST /tasks/:id/generate-subtasks` unconditionally — it ignores the toggle. Fix both call sites together if closing this gap.

## Conventions

- Keep the frontend as a single `public/index.html` file
- **A failed doc patch must not let the code commit through.** Writing CLAUDE.md/design.md edits as a `python3 - <<EOF` heredoc with `assert old in s` guards and then a *separate* `git add -A && git commit` line means an assertion failure skips the doc write while the commit still runs — code lands without its documentation, and the next session reads a file describing the old behaviour. Chain them (`python3 … && git add -A && git commit …`) or check `git diff --stat` before committing. This happened once in the 2026-08-16 header work.
- Backend changes require a restart under `npm start`. Use `npm run dev` (node `--watch`) if you want auto-restart during development.
- Database file is gitignored; it recreates on first run
- When editing the frontend, test via `http://localhost:3000` not `file://`
- New colors: use the sky-blue accent ramp above — do not introduce green
- **One popup box for everything.** `.team-popup` is the shared floating card and `.lock-popup-menu` / `.lock-opt` its row vocabulary. The lock popup, the **account popup** (sign out) and the **board popup** (delete board) all render into it — the last two share the single `#accountPopup` element. Any new small menu should reuse it rather than inventing a box: add the element id to `hidePopups()` and add its trigger's selector to `hidePopupsOnClickOutside()`, or the opening click will bubble to `document` and close the popup instantly.
- **Dark-mode overrides must out-specify what they're overriding.** `body.dark .thing` scores (0,2,1), which loses to any two-class compound like `.thing.modifier.modifier` (0,3,0). This has bitten twice: the signup form's project field (`.header-input.auto-generated.user-edited` pinned dark text on a slate input) and `.lock-opt` (light rows inside a dark popup). When adding a `body.dark` rule, check whether the light rule it's fighting is a compound selector, and match it.
- **Escape all user-controlled text at render time.** Any `${...}` interpolating a task/subtask description, project name, user name/initials/color, or error message into an HTML template must go through `escapeHtml()` (or `linkifyText()` for description fields, which escapes and then wraps URLs). This includes attribute positions (`placeholder`, `title`, `style`). A headless XSS render test recipe exists (jsdom, seeds hostile payloads via API, asserts inert render) — rerun it when touching render functions.
- **Schema migrations:** sql.js has no `ADD COLUMN IF NOT EXISTS`. Add columns via `ensureColumn(table, col, def)` in `db.js` (checks `PRAGMA table_info`), and add the column to the `CREATE TABLE` too. Runs on every boot; safe to leave in.
- **Foreign key cascades:** `db.js` sets `PRAGMA foreign_keys = ON` so the `ON DELETE CASCADE`/`SET NULL` clauses in the schema actually fire (sql.js defaults it off like stock SQLite). Gotcha: `db.export()` — called by `saveDb()` on every write — silently resets this pragma back off, so `saveDb()` reapplies it after every export. If cascades ever stop working again, this is the first thing to check.
- **Testing timezone behaviour without mocking the clock:** drive two requests with `x-tz: Pacific/Kiritimati` (UTC+14) and `x-tz: Pacific/Niue` (UTC-11). They are **25 hours apart, so their calendar dates always differ**, at every instant — no fake timers, no waiting for a particular hour. Assert that `due_today` counts a deadline in the zone where that day has arrived and ignores it in the zone still behind, and that an overdue task spills to the *caller's* today. For the frontend, run the jsdom test under `TZ=America/Chicago`: `process.env.TZ` is what jsdom's `toLocaleDateString` reads, so the real bug reproduces.
- **`node -e "require('./src/server.js')"` is not a syntax check** — it boots a listening server and hangs the tool call (and grabs port 3000). Use `node --check src/server.js`.
- **Local API testing:** boot a throwaway instance with `DB_PATH=<tmp> PORT=<free> ANTHROPIC_API_KEY=dummy node src/server.js` and curl the endpoints. Port 3000 is often taken by another local app — pick a free port. The frontend calls the API at a relative `/api`, so open it on whatever port serves `index.html`.
- **Quick frontend syntax check** (no browser): extract the inline `<script>` and run it through `vm.Script` in Node to catch broken template literals before shipping.
- **jsdom computes styles but renders nothing, so it cannot tell you a control is invisible.** The focus toggle passed every structural assertion — button present, class toggling, `aria-checked` correct — while being literally unseeable (a white 👻 at 45% opacity on a white header bar). **For anything where the question is "can you see it / does it read at size", render it through WebKit instead:** write a scratch HTML file with the icon at its real size beside its real neighbours and run `qlmanage -t -s 900 -o /tmp scratch.html`, then look at the PNG. Same tool the favicon work uses, same engine Safari uses. Structural tests and a render check answer different questions and neither substitutes for the other.
- **Headless frontend E2E** (proven pattern): `jsdom`'s `JSDOM.fromURL` against a throwaway server instance, with `runScripts: 'dangerously'`. Two gotchas: jsdom has no `window.fetch` — bridge it to Node's fetch resolving relative URLs; and use a unique company name per run (the subdomain UNIQUE constraint collides on a reused test DB).
  - **jsdom has no pointer, so `:hover` never matches.** Anything reading `document.querySelector('…:hover')` (`hoveredTaskRow()`) is untestable until you temporarily swap `document.querySelector` for one that returns the row you mean. Restore it immediately after — leaving it stubbed silently breaks every later assertion.
  - **Now that two hover targets exist, the `:hover` stub must answer for both.** Stubbing only `.task-arrow:hover` leaves the real `document.querySelector` answering `.task-item:hover` — which in jsdom is `null` anyway, so it happens to work; but a row-hover stub must explicitly return `null` for `.task-arrow:hover`, or the arrow branch (checked first) swallows the digit and the reorder assertion fails for the wrong reason.
  - **Top-level `let`/`const` in the page are NOT on `window`** — `w.tasks` is `undefined`, and reading it throws inside the test rather than failing an assertion. Function *declarations* do become window properties, which is why `w.restoreSession()` and `w.getTodayKey()` work. To assert on task state, re-fetch it from the API instead of reaching into the page.
  - **jsdom has no `Element.scrollIntoView`**, and `selectDay()` calls it on a 0ms timeout — so any test that clicks a day card prints a `TypeError: card.scrollIntoView is not a function` *after* the assertions have already passed. It's a harness gap, not a bug; stub it (`w.HTMLElement.prototype.scrollIntoView = () => {}`) if the noise gets in the way.
  - **A task row's own `textContent` starts with the completion circle and the → arrow**, never the task name. Find rows via `.task-description` and `.closest('.task-item')`; `row.textContent.startsWith(name)` silently returns nothing and every downstream assertion then fails for the wrong reason.
- **Testing anything that calls Anthropic:** copy `src/` and `public/` to a scratch dir, symlink the real `node_modules`, and replace `src/ai.js` with a stub exporting the same surface (`generateSubtasks`, `researchSubtasks`, `triageCosts`, `takeUsage`, `COST_MIN_CONFIDENCE`). The server picks it up with no flag or env var because it only ever `require('./ai')` lazily. This is how the whole two-phase research path — the 0.8 replacement gate, index matching, mid-flight ticks, budget exhaustion — was verified without spending a cent, and a stub with a deliberate delay is the only way to test what happens *while* research is running.
  - Keep the stub's fixture text stable across runs. Four "failures" in a regression sweep turned out to be a stub that had renamed its tasks, not a regression.
- **Testing a schema migration:** build a database with the current code, then `ALTER TABLE … DROP COLUMN` the new column back off it (sql.js's SQLite is new enough), and boot the server against the result. That is a genuine pre-migration database, and it is the only way to prove a backfill produces the order users currently *see* rather than insertion order. Boot a second time to prove it's one-shot.
  - To reach a signed-in board without driving the signup form: seed the API via fetch, set `localStorage['movealong.session'] = JSON.stringify({subdomain, slug, projectId})` (exact keys — `slug`, not `userSlug`; wrong keys fail silently to the signup screen), then call the app's `restoreSession()` and wait for render.
- **HTML5 drag & drop:** `dragstart` must call `e.dataTransfer.setData('text/plain', ...)` or Safari never initiates the drag. `.task-item` already has `user-select: none`, which drag also needs.
- **Safari ignores `focus()` on elements inside a `visibility: hidden` subtree.** The modals fade in via `visibility` + `opacity` transitions, so focusing a field in the same tick as adding `.visible` silently fails — defer it (`setTimeout(() => input.focus(), 50)`, see the New project modal).
- **Help-page vignettes (`help.html`):** feature cards get looping pure-CSS mini-scenes in column 2 of the `three-col` grid, built from a shared vocabulary (`.mini-card`/`.mini-task`/`.mini-circle`/`.mini-day`, real dates via `data-day-offset`, one storyline: building a backyard fence). Section order: The board (Add · Move forward · **Lock a deadline** · Complete/postpone · Overflow · Projects) → **More fun** (Links, Prioritize, **Repeat**, Create lists, **Dark mode**, **Focus on one day**) → Power moves → Subtasks → **Add calendar events (Beta)** → Run your own copy → Enabling real AI steps.
  - **A demo can claim column 3** (`.card.demo.demo-3`, normally the margin-note column) when the card's point *is* a comparison — Projects puts a deadline-flagged tab bar there, Dark mode puts the dark still there. Under 760px it falls back to `grid-column: auto` and wraps, since the third column and the margin notes both disappear at that width.
  - **The two light/dark stills hard-code their own chrome colours** instead of inheriting. Every other scene stays light in dark mode; these two must each keep their own theme in *both* modes or the card stops making its point.
  - **Scene CSS declared above the `.nav-ring` block must compound its selectors.** `.scissors-ring` gets away with a bare class only because it's declared *after* `.nav-ring`; a ring style written up in the scene sections (e.g. `.spill-ring`) loses the source-order tie and must be written `.nav-ring.spill-ring`. Same for its `ellipse` animation override. This cost two debugging rounds. In the header, the theme toggle sits **right** of "← Back to your board" so the link's arrow doesn't point at it. Hard-won rules:
  - **Never stagger elements in an infinite loop with `animation-delay`** — the delay permanently phase-shifts that element against the scene's shared fade, so it lingers into the next cycle. Give each element its own `@keyframes` with percentage offsets on the same duration (`stepIn1..5`, `clock1..3`).
  - **Pin `opacity` (and any reset property) at every visible keyframe.** A property keyed only in the last few keyframes interpolates from its implicit start value across the ENTIRE cycle — the chain scene's dragged task faded over the whole 8s and was near-invisible by the time it "landed" on Thursday. If a keyframe block ends with `opacity: 0` for the loop reset, earlier frames need explicit `opacity: 1`.
  - **Anchor animated cursors inside their click target** (`top:50%; left:50%`, so `translate(0,0)` = target center; the rest position is an offset in the keyframes). Absolute scene coordinates misaligned twice (prio and done scenes) because font metrics shift row positions a few px.
  - **Red attention ring** = an SVG `<ellipse pathLength="100">` in a `.nav-ring` svg absolutely positioned inside the target, drawn by animating `stroke-dashoffset` (`ringDraw`), tilted a few degrees for a hand-drawn feel. Resize per target with a second class (`.scissors-ring` pattern).
  - Every scene needs `prefers-reduced-motion` end-state overrides in the shared reduce block; scenes intentionally stay light in dark mode (see Dark mode above).
- **Margin notes (help page, column 3):** `.margin-note` = hand-drawn SVG arrow + handwriting font stack (`Bradley Hand`/`Segoe Print`/`Comic Sans MS`/cursive — system fonts, no webfont), written in Kevin's first-person voice. Default **green `#059669`** (`#34d399` in dark) — the one sanctioned green in the project, approved 2026-08-05 for these annotations only, precisely because they should read as outside the app's palette. `.margin-note.important` = red `#ef4444` for the notes that matter most. Pinned `grid-column: 3`, `display: none` under 760px. Source order decides the row: place the note right after that row's demo card (or the help card when there's no demo).
- **Every help vignette also lives standalone in `docs/animation/`**, one file per scene plus an `index.html` contact sheet, so a single animation can be watched and reworked without the surrounding page. They are **generated, not hand-copied** — `node docs/animation/build.js` re-extracts all of them from `help.html`, which stays the source of truth, so they can't drift. Each extract embeds the *entire* help stylesheet rather than a sliced subset, so it's pixel-identical rather than approximately right (~58 KB/file, fine for a local tool). Rerun the build after touching any scene.
- **When the constraint is width, one of the mockups must spend it differently.** The 2026-08-16 subtask-row set (`archive/st-v*.html`) offered four ways to arrange controls and three of them put the controls on their own *line*; the winner shipped and was reversed to a vertical rail within hours, because a whole line per row is a worse price than 24px of width — and the mockups' short sample steps hid that. If a variant set is about reclaiming space along one axis, include at least one that reclaims it along the other.
- **UI design exploration:** iterate with self-contained static mockups in `archive/` (gitignored) — one file per variant (`pm-v1.html` … `pm-v9.html`), each replicating the real board's CSS (white 200px day cards, blue today, real task-row anatomy) with a cross-linked nav bar and an explainer box, using real scenario data. The maintainer picks/combines across variants ("v9 = v6's circle + v8's numbers, reversed"); build the winner only after they converge. Don't prototype inside `index.html`.
- **New interactive features: reuse an existing idiom before inventing a UI primitive.** When a feature idea implies a new selection/hit-testing model (e.g. "click the SVG thread between two chained tasks and hit Delete"), check whether an existing per-row pattern already covers it — hover-reveal icon (`.task-lock`, now `.task-unlink`), hover+keypress (priority 1/2/3), or click-to-popup (lock popup) — before building the novel interaction. The `#chainOverlay` SVG threads are intentionally `pointer-events: none` and redrawn only on hover, so making them clickable would require adding persistent rendering, per-segment task-id metadata, and a new hit-testing/selection concept from scratch. The unlink feature shipped instead as a hover-reveal ✂️ next to the chained row, matching `.task-lock`'s existing pattern — cheaper, more consistent, and it reused `spliceOutOfChain`-adjacent server logic (a new `parent_task_id = NULL` update) with no new frontend primitives.
- zsh gotcha: don't name a shell variable `UID` in test scripts — it's read-only and the assignment errors out.
