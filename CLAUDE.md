# Move Along (product name: MoveIt since 2026-09-13)

A task management app that moves ideas into action and reduces decision-fatigue: a task or subtask can be postponed (moved), completed, or assigned to a human or AI agent in one click.

## Vision

1. **Move ideas into action** — when a task is added, Claude immediately populates a subtask pane with the steps to complete it.
2. **Reduce decision-fatigue** — every subtask has a default assignee (AI or human), assignable with one click. AI agents research options, fetch prices, check weather, and return actionable information.

Tasks can be sent to an AI agent, not just humans. Cross-user collaboration is back-burnered — focus is the single-user + AI-agent loop.

## Core Concepts

### Projects
The basic unit is a **project page** (the 30-day calendar board). A user can create many projects under one username ("personal", "doghouse", "financial"); each is its own board.

### Tasks and Subtasks
- Adding a task to a day opens a **subtask pane** beneath the day pane, populated by Claude with up to **7 subtasks** (prompt asks for 5-7; the generate-subtasks endpoint hard-caps AI and mock lists at 7).
- After the initial subtasks appear, a deeper analysis using agents reviews proposed solutions and fetches data (Amazon prices, weather, etc.) to refine them.
- Each subtask has an **emoji for the default assignee**: 🧠 AI agent, 👩 human. Clicking the emoji assigns.
- **Dependent subtasks** are indented (3 spaces) under their parent in light grey and move with the parent when assigned.

### Subtask Quality: Actionable, Not Generic
Subtasks must be **specific, actionable, research-backed** — never PM filler.

Bad: "Define requirements and scope", "Research materials and tools needed", "Create a detailed plan".
Good: "Pick a location — sunny, 5-10 ft high, near trees (birdsonly.com/placement-guide)", "Choose target birds for your area (audubon.org/native-plants/98101)", "Decide: buy plans online ($5-15 on Etsy) vs design your own", "Get materials — cedar boards, screws, waterproof glue (Home Depot list)".

**Concise (Kevin, 2026-09-16: "way too verbose"):** the draft prompt's rule 0 caps a step at ONE action, under 12 words before any link, verb first, one link at most, no rationale clauses — the pane is 178px wide. The list prompt (12) and research pass (14) already carried caps; the ordinary draft had none.

Principles: prefix a mini-label when helpful ("Project plan:", "Decision:", "Research:"); include real, relevant links (retailer searches, guides, location-aware resources); surface the actual decisions ("Decide: cook vs cater vs potluck (Thumbtack caterers near you)"); be domain-specific (bird species and wood types, not "gather materials"); AI-assigned subtasks return concrete options, prices, links and comparisons, not summaries.

### Two-phase subtasks (draft now, research behind it)
- Adding a task runs **phase 1**: a fast reasoning-only call returning 7 steps in seconds — engage the user's brain immediately, not be right yet.
- **Research is opt-in, per step (since 2026-08-16).** `projects.research_enabled` defaults to **0**; the trigger is the **🔎 on each step's rail** (`POST /api/subtasks/:id/research`). The pane-wide "Research these steps" button is gone — researching all seven decided *for* the user which steps were worth money when only two or three are. The **🔎 Research switch in the header** (beside 🧠) makes every new task research automatically. Off by default because at ~$0.10 a researched task, auto-researching everything empties a $5 board in about a week.
- **↺ never researches**, switch or no switch (`req.body.regenerate === true`). Topping up one row costs a whole search budget (`max_uses` is per call, not per row).
- **Phase 1 drafts on Opus 5, research on Sonnet 5 (2026-09-08).** `ai.js`: `DRAFT_MODEL = 'claude-opus-5'` with `output_config: { effort: 'medium' }` and a 30s abort; `MODEL = 'claude-sonnet-5'` for whole-task and single-step research. The draft is judged on whether the first step is the right first step (judgment, ~2-3¢ a draft); research is search-bound and Sonnet + `web_search` is already the cheap configuration. **Kevin's premise was that the draft ran on Haiku; it never did** — Haiku only does cost triage. Fable 5.1 was declined for the draft (5× Opus, thinking floor, needs `refusal` handling and a 30-day retention org setting); it's a candidate for agent dispatch. `max_tokens` went 2048 → 4096 because thinking tokens count against it. **Opus latency was not measured before shipping** (no local key; `railway run` was blocked by the permission classifier) — if drafts feel slow, `DRAFT_EFFORT = 'low'` is the first knob. Add a `RATES` row whenever a model constant changes; `meterUsage(data, DRAFT_MODEL)` is passed explicitly.
- **Phase 2 (`runResearch()` in `server.js`) runs behind the HTTP response**, fire-and-forget, with the Anthropic `web_search` tool, rewriting rows **in place**. It never adds, removes or reorders steps: results match back **by index**, and every row is re-read immediately before writing so a row the user ticked or promoted mid-flight is skipped, not resurrected. Load-bearing — research takes 15-60s while the user watches the pane.
- **A step is replaced outright only at ≥ 0.8 confidence** (`RESEARCH_REPLACE_CONFIDENCE`). The model returns `refined` (always) plus `illogical`/`confidence`/`replacement`; the gate is server-side. Ordinary vagueness is refined, never replaced.
- **`subtasks.provisional` = "awaiting research"**, watched by the frontend poll; set only when phase 2 will actually run. It no longer changes how a row looks — a draft is a finished state.
- **`subtasks.researched` marks rows the pass rewrote**; they render **light blue** as a row tint (`#f0f9ff` + inset `#7dd3fc` edge) with blue-tinted text, *not* blue text alone — AI steps are full of `.task-link` anchors at `#0284c7`, and blue text around blue links is unreadable. Any "colour the text" request in the pane hits this wall.
- **The frontend polls** (`pollResearch()`, 3s, capped ~2 min) while an open pane holds a provisional row — no websockets, no queue. Close the pane and research still finishes. `repairInterruptedResearch()` clears the flag on boot (a restart mid-research would otherwise leave rows greyed forever).
- **`runResearch` must call `flushDb()` itself** — `res.on('finish', flushDb)` already fired for the request that started it (same trap as calendar sync).
- **Per-step research runs at `SINGLE_STEP_SEARCHES` (2), not the whole-task 5** — `max_uses` is per call, so one row at the batch budget costs as much as all seven. It **writes the same three-state cost fields** as `runResearch()` (without that, a row researched from its own button silently got no price) and skips cost triage (triage aims a shared budget across seven rows; nothing to aim with one).

### Keeping the pane at seven
- **Regenerate (↺) tops up and drafts only; no wipe, no research.** It used to `DELETE FROM subtasks WHERE task_id = ?` and destroy user-typed steps. Now every pending row survives, only freed slots refill, and kept steps are shown to the model so it doesn't re-propose them. A full pane returns `full: true` and spends nothing.
- **No delete affordance on a subtask row** — **ticking a step off is the only way to free a slot**. `DELETE /api/subtasks/:id` exists but nothing in the frontend calls it.
- **A list pane is exempt from the top-up** ("My list" and "Suggestions" are separate sections); its AI rows are still replaced wholesale.
- **Hover a step and click ↑ to promote it onto the board** as a real task. It lands on the **parent task's day, not today**, goes through `findDayWithCapacity()`, and leaves the pane (frees a slot).
  - ↑ is **always visible** since 2026-08-16 (a hover-reveal can't be discovered by looking; the rail can afford it). **The board's hover-reveals stay** — one-line rows can't spare the width. Withheld on list-pane suggestion rows, where ↑ means "move to my list".
  - Promoting lifts dependents to the row's own parent first; `parent_subtask_id` is `ON DELETE CASCADE`, so skipping that destroys them.
  - **The promoted task lands directly under its source task, and its circle carries a dot.** `tasks.promoted_from` records the source; `placeTaskAfter()` splices at `parent.position + 1` and renumbers the day. Hovering the promoted row tints its source (`.source-highlight`). **Indenting or greying it would be wrong** — that's the pane's vocabulary for dependents. The dot uses `.task-circle:empty::before`, so it's withheld when the circle has a series countdown or completed check.
  - Placement is skipped when `findDayWithCapacity()` overflows onto **another day** — it appends there, keeping the dot and hover link.

### AI budget (per board, per month)
- `projects.ai_budget_usd` — whole dollars, **default $5** (cents-level control is exactly the decision this app saves people from).
- **On/off = the 🔎 Research switch in the header** (`#researchSwitch`, same `.assistant-switch` markup as 🧠 and 📅). State is **per board** (`projects.research_enabled`), unlike its neighbours (per browser) — it spends *this* board's money, so it repaints from `refreshBudget()`.
- **Turning it ON opens a cost dialog** (`#researchWarnModal`): ~$0.10 a task, this board's spend so far, a **Change budget** link, and **Don't warn me again** writing `localStorage['movealong.researchwarn'] = 'off'` (per browser — it records that this person has read the price). Turning it **off** never warns.
- **`#budgetBar` under the board is gone** (2026-08-14). Spend is in the switch's `title` tooltip, and **Shift+Click the switch edits the budget** (same idiom as Shift+Click 🧠 for the AI key). That's the *only* permanent path to the budget after the dialog is dismissed; the over-budget toast is the other reminder.
- **It gates research only.** Phase 1 always runs — an exhausted board still drafts steps, marks them final, and says so (`research_status = 'over_budget'`).
- Spend is metered from the API's own `usage`, **including `server_tool_use.web_search_requests` at $10/1000**, one row per call in `ai_usage` — an audit trail, not a counter. Rates live in one constants block at the top of `ai.js`; nothing reads a live price list.
- **~$0.10 per researched task** at `max_uses: 5` — about half is the searches ($0.01 each), so `max_uses` is the real cost lever. $5 ≈ 50 tasks. (Haiku cost-triage adds a fraction of a cent.) **Per-step research changed the arithmetic:** seven steps one at a time ≈ $0.21 (7 × 2 searches) vs ~$0.10 batch — cheaper per click, pricier if someone researches everything; the intended trade.
- **`ai.js` rates are hand-maintained and per-model.** Sonnet 5 is $2/$10 per MTok where Sonnet 4.6 and earlier were $3/$15. Re-check the pricing page when `MODEL` changes; cache reads bill at 0.1x base input and writes at 1.25x — folding them into base input overcharges reads 10x.
- **Mixedbread's *Toast 1* search agent was evaluated and declined (2026-08-16):** $0.016–0.023/query, ~8s median. Its "10x cheaper than a frontier model" compares against a frontier model *as the search agent*, which this app doesn't do; the saving is a few cents a task against a $5 cap for a second vendor and failure mode in the path the user watches live. **Revisit only if** research latency becomes the complaint (8s would delete `pollResearch()`) **or** step pricing pushes past `max_uses: 5`. First settle whether it searches the open web or only an indexed corpus, and whether it returns the index-matched structured objects the pass needs.
- **`AI_LIMIT_*` and this budget differ:** those are abuse brakes on a public deployment (per IP, per day); this is the owner's own cap.
- `web_search` takes `user_location`; the only location known is the IANA zone from a connected **calendar feed** — enough to localize "stores near me".
- Calendar rows carry `project_id = NULL`, so they have no board to bill and are never researched.

### What a step costs (materials, labour, services)
- **Two different costs, never one number.** `ai_usage` is metered actuals. `subtasks.cost_*` is an *estimate about the world* — uncertain, local, time-varying. Never add them together.
- **Written only by the research pass, as extra fields on each verdict** — a separate cost call would double the search budget for information the model already had.
- **A Haiku 4.5 triage call runs first** (`triageCosts()` in `ai.js`), labelling each step `material | labor | service | none`. Most are `none`; labels ride into the research prompt so searches concentrate on the rows that spend. The point is the search budget, not the token saving. Triage failure is caught and logged; research decides for itself. It gets its **own `ai_usage` row** (`kind = 'cost_triage'`).
- **Ranges only**, never point estimates; `cost_basis` ("24x 6ft cedar picket at $4.28") is **required**. `cost_source_url` and `cost_as_of` ride in the chip's tooltip — a price with no date is worse than none.
- **Three states:** a priced row; `cost_kind = 'none'` (research ran, spends nothing — an *answer*); `cost_kind = NULL` (never researched, or too shaky). The pane's total prefixes **≥** whenever any pending row is NULL.
- **The confidence gate lives in `runResearch()`** beside the 0.8 gate. `COST_MIN_CONFIDENCE` is **0.5** — lower because it only guards adding a figure the user can take or leave, and a range carries its own uncertainty. Below it the estimate is dropped.
- **Rendering:** grey chip after the step text (`.subtask-cost`), an `<a>` when a source URL exists; task total opposite the title in the pane header (`.subtask-cost-total`). Whole dollars — "$91.40–$127.75" claims false precision.
- **`ai.js` rates are a per-model `RATES` map**; `meterUsage(data, model)` takes the model explicitly.

### The brief (/brief/:projectId, 2026-09-02)
- **Standing notes the assistant reads before every AI call.** **Two layers merged at call time**: `users.brief` (personal, every board) then `projects.brief` (this board). `briefFor(ownerId, projectId)` in `server.js` merges and feeds phase 1 (`generateSubtasks`), cost triage, whole-task research and single-step research. Not mocks; ↺ gets it via generate.
- **Freeform, one note per line, bullets optional.** Rules, preferences and facts all reach the model as context; classifying each line is the decision the app exists to delete. Server strips a leading `- * •`. No length cap (a cap would inhibit "learning" him); containment comes from the next two points.
- **Triage filters, research sees only what fits.** `triageCosts()` takes the brief and returns `{costs, brief}` — indexes of notes that bear on this task. `runResearch()` passes only those lines. If triage fails, research sees everything. Phase 1 and single-step research get the whole brief.
- **Every call reports back** — with a brief present, the prompt asks for `{"steps": [...], "brief_used": [indexes], "question": "..." | null}`; `unwrap()` in `ai.js` accepts either shape. `takeBriefReport()` mirrors `takeUsage()`. `applyBriefReport()` in `server.js` upserts `brief_usage` (keyed by **line text**, per scope + owner) and inserts the question into `brief_questions` — deduped case-insensitively against open questions, **capped at 7 open per board** (`BRIEF_QUESTION_CAP`).
- **The page** (`public/brief.html`, one static file like `/task`) is **two columns**: an inbox pane *"The assistant wishes it knew"* on top (blue; each question shows its task; answer goes into **About me** on Enter or **This board** on ⌘⏎, or **skip**). **Left, quick forms:** **You** (full name, goes-by, phone, email, address, Discord, notes) and **Health** (allergies, medications, conditions, doctor, pharmacy, emergency contact + phone, notes) — label-over-field, autosave on input/focusout, stored as JSON in `users.brief_contact` / `brief_medical`, each filled field becoming one `Label: value` line. **Right, open-ended:** **About you**, **Travel**, **About this board** — autosaving textareas, with *What the assistant has used* beneath (lines by use count, never-read greyed). The page reads the person from `localStorage['movealong.session']` and sends `x-ai-key`.
- **About you and About this board maintain themselves — the task monitor.** Each has a `brief_learned` list (newline text on `users` / `projects`) rendered under the textarea in **full colour, not grey** (Kevin: "they shouldn't be in gray"). `POST .../brief/learn { scope }` runs `learnBrief()` in `ai.js` (no tools, ~1k tokens) with pinned lines, current learned list, rejected list and the last 40/60 task descriptions, storing the **complete new list** (max 8). ### The Lists page (/lists, 2026-09-22)
- **A list you'll want again shouldn't expire with the day it was written on.** "list things to take to Seattle" on Sep 19 becomes **Travel**, kept on `/lists`, and dropped onto any day as a fresh copy.
- **Board → page MOVES; page → board COPIES** (Kevin's calls, 2026-09-22). The master is a library card, not a token: it stays on the page, and **every copy starts with nothing ticked**, so ticking "passport" off in Seattle never erases it from the list he keeps. **AI suggestions don't follow** — they were a board-time helper; shelving drops them along with anything already ticked.
- **`tasks.shelved` (0/1) is the whole mechanism.** A shelved list is an ordinary task row with ordinary subtasks as its items — no second store, no second item type — so the page reuses `POST /tasks/:id/subtasks`, `PUT|DELETE /subtasks/:id` and `PUT /tasks/:id { description }` (rename) untouched. The cost is that **every board query must carry `COALESCE(shelved,0) = 0`**: spillover, autolock, the board read, `due_today`, the List view, the shared board, `findDayWithCapacity()` and `bumpableTaskOn()` (same trap as `t.goal` — a hand-listed SELECT or a COUNT that forgets it puts a phantom row back on a day).
- **Routes:** `GET|POST .../lists`, `POST /api/tasks/:id/shelve`, `POST /api/tasks/:id/unshelve { scheduled_date, project_id }`. Unshelve refuses a past day, and **skips `findDayWithCapacity()`** — a list is a box under the add-task input, not one of the day's seven rows, so it neither fills a day nor bumps anybody. Shelve also splices the row out of its series and clears `locked`/`goal`/`repeat_rule`/`due_date`/`position`.
- **The name carries the prefix across the boundary.** The board decides a list pane by reading the description (`LIST_TASK_RE`), so the master is filed as **"Travel"** (`listNameFrom()` strips a leading `list`/`list:`) and the copy goes back as **`list: Travel`** (`boardDescriptionFor()`). Rename the master to anything; the trip back re-prefixes.
- **A boxed list keeps → and 📅, never drag (Kevin, 2026-09-22).** They carry the *same* `.task-arrow` / `.task-lock` classes a task row uses, so the existing click wiring, the lock popup and **hover-the-arrow-and-press-1-9** work with no second code path; the box shows 🔒 when locked. **The inline-edit resolver has to exclude them** — `tryInlineEdit()` runs in the capture phase and would otherwise swallow Shift+Click-the-arrow (+1 week) and rename the list instead.
- **A copy pushes its edits back up: `Update “Travel”`** replaces the footer's Keep button whenever the row has a master (`tasks.list_master_id`, set at unshelve, `ON DELETE SET NULL` so deleting the master just unlinks the copy). `POST /api/tasks/:id/sync-master` makes the master's items **the copy's items — all of them, ticked or not, and all unticked on the master**: a tick on a copy means packed, not "drop it from the list I keep" (Kevin's call). Removal for good is a Lists-page gesture only. **The name is deliberately not synced** — renaming a copy "list: Seattle trip" for one trip must not rename the list you keep. A copy with a master is never offered Keep, or the board would grow a second "Travel".
- **`listMasterOf` (taskId → {id, name}) is filled from both task reads** — the board's and the List view's — because a pane opens on either; both SELECTs carry `t.list_master_id` and a `LEFT JOIN tasks lm` for the name (the usual hand-listed-SELECT trap).
- **The doors are sentences, not glyphs.** The list pane's footer (`.list-foot`, a dashed pink rule) holds two: **`Keep on the Lists page`** / **`Update “Travel”`** on the left and **`Delete`** on the right (`.list-keep` truncates a long master name; the tooltip carries it whole). A 178px column has room for four words, and these are the controls that act on the *whole* list rather than a row of it. The page's own door is a **lists icon in the header, right of the dashboard icon** (Kevin, 2026-09-22 — the group reads notes · dashboard · lists, and its leftmost, `#notesLink`, carries the `margin-left: auto` that floats the middle group).

It confirms first, and on a copy both the confirm and the toast say the master on the Lists page is untouched. (Ordinary step rows still have no delete; this deletes the *task*, via `DELETE /api/tasks/:id`.)
- **The page** (`public/lists.html`, one static file like `/notes`): composer on top (Enter names a new list), CSS-columns masonry of cards with a **pink left edge** (the list's colour, same as the board's box and pane). Per card: click the title to rename, an **empty circle removes an item** (the suggestion-dismiss idiom — a master has nothing to tick off; ticking is what you do to a copy, on a day), **click an item to edit it in place** (Enter or blur saves, Escape cancels — the board's inline-edit idiom, not a `prompt()`), an add-item slot, then board + day pickers and **Put on the board**, with Delete opposite.

### Series (task chains / dependencies)
- **User-facing copy says "next step in a series" — never parent/child** (rewritten 2026-08-05). `parent_task_id` is internal.

- **Hover threads:** hovering a member lights the family (background tint), fades the board (`.board-container.threading`), and draws SVG bezier threads (`#chainOverlay`) between consecutive members. Hover-only. Colors from `CHAIN_COLORS` (violet/orange/fuchsia/indigo/cyan — no red, no green) keyed by root id; **only on hover**, resting board monochrome.
- **Move cascade:** changing a member's date (→, lock popup, any `PUT` with `scheduled_date`) shifts every later step by the same delta. **Stops at the first locked step** and **skips completed steps** without stopping. Earlier steps never move.
- **Spillover cascades too:** an overdue member spills to today and drags successors forward by the same delta (same lock-stop rule).
- **Boot chain repair:** `repairCompletedChainLinks()` splices any completed task still holding chain links (re-fetches each row before splicing). Idempotent.
- **Series never break:** assigning, deleting, or **completing** a member splices it out (`spliceOutOfChain()`). Completing severs one-way (reopening doesn't restore). Re-dropping a chained task repositions it. Frontend: `toggleComplete()` must `loadTasks()` when completing a chained task because the splice rewrites *other* rows. Consequence: countdowns renumber on completion, and a 2-step chain dissolves when either member completes.
- **Unlink:** hovering a chained pending task (day board) reveals ✂️ when it has a predecessor — the chain ROOT never shows scissors (no parent edge); cut a 2-chain from its child. Recurring support question, not a bug. Clicking (with confirm) cuts one edge — `POST /api/tasks/:id/unlink` nulls `parent_task_id`, leaving successors attached (the task becomes a new root). Distinct from `spliceOutOfChain()`.
- Frontend: `computeChains()` builds `chainInfo` (task id → chainId/countdown/color) on every `renderBoard()`. After any date change, `loadTasks()` refetches because cascades change other rows.

### Hyperlink tasks
- Any URL in a task's text renders as `.task-link`, **opens in a new tab** (`target="_blank" rel="noopener noreferrer"`). Day board, Main page, and subtask rows; forwarded/placeholder rows stay plain.
- `linkifyText()` escapes the whole description first, then wraps `TASK_URL_RE` matches (`http(s)://…` and `www.…` **only** — so `javascript:` can never become an href). Trailing `. , ) ] ' "` trimmed. `www.` gets `https://`.
- Descriptions are **HTML-escaped now** (they used to inject raw — an XSS hole).
- Links carry `draggable="false"` so dragging from a link starts the series drag.
- Both description click handlers early-return on `e.target.closest('a.task-link')`.
- **URLs in subtask rows render as a link glyph, not text** (`linkifySubtask()`; board rows keep `linkifyText()`). The glyph sits **where the URL was**; hover shows the **domain**. Wrapping parens are eaten with the URL, surrounding whitespace is not.
  - **`SUBTASK_URL_RE` matches bare domains, which `TASK_URL_RE` never did** — the model writes `homedepot.com/s/cedar`, so AI links cost URL width *without being clickable*. Bare form is admitted only against `SUBTASK_TLDS` (keeps `$4.28` and `1.5in` out); href always rebuilt with `https://`.
- **Completing any task closes its subtask pane** (`toggleComplete()` drops it from `expandedTaskIds` on `willComplete`). The URL gate and `taskHasLink()` were removed 2026-08-05.

## Architecture

- All frontend state loads from API on signup; no local persistence
- Tasks have an owner (whose board) and optional assigned_by (who gave it)
- **No `assigned_to` column; assignment is not a flag.** `POST /tasks/:id/assign` rewrites `owner_id` — the row *moves*. Any `owner_id`-filtered query already excludes assigned-away tasks; adding `assigned_to IS NULL` is a 500 (`no such column`). The frontend's `task.assigned_to_id` is a **client-side optimistic field only**, set by `assignTaskToMember()`; it never comes back from the API.
- Companies use subdomain-based URLs: `{subdomain}.movealong.com/{user_slug}`
- Database auto-creates; writes mark it dirty and it persists **once per HTTP request** (`flushDb` on response finish, plus SIGTERM/SIGINT) via atomic tmp-file + rename in `saveDb()`

## API Pattern

All under `/api`, RESTful JSON.
- Companies: `POST /api/companies` (**sign in *or* sign up** — an existing team + user name returns that account with `returning: true`; a known name is the credential), `GET /api/companies/:subdomain`
- Users: `GET|POST /api/companies/:subdomain/users`
- Tasks: `GET|POST /api/companies/:subdomain/users/:slug/tasks`
- Task actions: `PUT /api/tasks/:id`, `POST /api/tasks/:id/assign`, `POST /api/tasks/:id/return`, `DELETE /api/tasks/:id`

Full reference: `reference/api-reference.md`. Schema: `reference/data-model.md`. Check those before re-deriving.

## Key Design Decisions

- No authentication yet (URL-based access; auth is planned)
- Frontend is a single HTML file with inline CSS and JS; sql.js avoids native compilation
- 30-day calendar view with horizontal scroll
- Incomplete past tasks spill to today automatically — **except locked tasks**
- **Day keys are UTC-anchored labels, but *which* label is today is a local question.** `YYYY-MM-DD` keys and their arithmetic (`addDays`, `addMonths`, `generateDays`) stay UTC-anchored. Until 2026-08-14 today came from `new Date().toISOString()` on both ends: at 9pm CST the board read Saturday and spillover moved tasks early.
  - **Frontend:** `getTodayKey()` is `new Date().toLocaleDateString('en-CA')` (formats as `YYYY-MM-DD`). `getTomorrowKey()` builds off that key.
  - **Backend:** every request-scoped today goes through **`todayKeyFor(req)`**, reading an **`x-tz` header** (sent by `api()` on every call) and formatting through `Intl`. Unknown/absent zone falls back to UTC. No schema change, nothing cached.
  - Sites: spillover (`GET .../tasks`), `due_today` on `GET .../projects`, subtask return, calendar sync's `todayKey`. Any new server "today" belongs there too.
  - Not covered on purpose: `monthKey()` for the AI budget is still UTC.
- Day cards are **200px** wide. The subtask pane hangs absolutely below its day column at `width: 100%` — **never wider than its day**.
- **The board clips vertically, and the pane lives inside that clip.** `.board-container` sets `overflow-x: auto`, which computes `overflow-y` to `auto` too, so the container cuts off anything hanging below — and `.subtask-pane.board-pane` is absolute at `top: calc(100% + 10px)`. `padding-bottom` on `.board-container.has-expanded` buys the pane room. A flat **440px** guillotined tall panes (a 7-step pane runs ~640px), and `scrollbar-width: none` made it read as a hard wall. **`fitExpandedPane()` measures the open pane and sets `padding-bottom` inline** — columns are `align-items: flex-start`, so `pane.offsetTop + pane.offsetHeight` is comparable to the tallest column. Runs at the end of `renderBoard()`; every pane-height change re-renders through `renderView()`. 440px is kept as a pre-measurement fallback. **Any new absolutely-positioned board child must be reserved for in `fitExpandedPane()`.**
- Subtask pane: one contained card of up to 7 AI steps (plus user-added) as compact rows, ↺ "Regenerate all steps" top-right. **Controls live in a narrow vertical left rail (`.subtask-rail`, 18px) — check · assignee emoji · ↑ promote · ↻ re-research, stacked** (redesigned 2026-08-16 from `archive/st-v1..v4.html`; v2's horizontal strip shipped first, the rail replaced it same day). The pane has ~178px usable; the old inline row spent ~60px on controls, the strip a whole *line* per row. The rail costs ~24px and no line. **Trade: height on rows with all four icons**; if that bites, the fallback is a 2×2 rail, not the strip. Dependents indented. **Completed subtasks disappear from the pane** (filtered at render; server keeps them for List's n/m count) — no way to un-check from the UI.
- **The → arrow is gone (2026-08-16), replaced by ↻ "Research this step again".** → said "Send to AI agent" while re-researching. ↻ calls `researchSubtask()` / `POST /api/subtasks/:id/research`, shown **only on rows research has been through** (`st.researched`). ## Conventions

- Keep the frontend as a single `public/index.html`.
- **A failed doc patch must not let the code commit through.** A `python3 - <<EOF` heredoc with `assert old in s` guards followed by a *separate* `git add -A && git commit` line means an assertion failure skips the doc write while the commit runs. Chain them (`python3 … && git add -A && git commit …`) or check `git diff --stat` first. Happened in the 2026-08-16 header work and again 2026-09-13.
- Backend changes require a restart under `npm start`; `npm run dev` auto-restarts.
- Database file is gitignored; recreates on first run.
- Test the frontend via `http://localhost:3000`, not `file://`.
- New colors: the sky-blue ramp — no green.
- **One popup box for everything.** `.team-popup` is the shared card, `.lock-popup-menu` / `.lock-opt` its rows. The lock popup, **account popup** and **board popup** all render into it (the last two share `#accountPopup`). New menus reuse it: add the element id to `hidePopups()` and the trigger's selector to `hidePopupsOnClickOutside()`, or the opening click bubbles to `document` and closes it instantly.
- **A native form control (`<select>`, `input[type=date]`) ignores your colours until `appearance: none`.** WebKit paints it from the UA stylesheet, so a `body.dark` rule setting `background`/`color` leaves a white box on a dark card however specific it is; `color-scheme: dark` on `body.dark` helps in Safari but not in a qlmanage shot. Turn the appearance off and draw the control yourself — then a select's caret is a data-URI background image, and the dark rule must use **`background-color`, not the `background` shorthand**, or its higher specificity wipes the caret out.
- **Dark-mode overrides must out-specify what they override.** `body.dark .thing` (0,2,1) loses to `.thing.modifier.modifier` (0,3,0). Bitten by `.header-input.auto-generated.user-edited` and `.lock-opt`. Match the compound.
- **Escape all user-controlled text at render time.** Any `${...}` of a task/subtask description, project name, user name/initials/color, or error message goes through `escapeHtml()` (or `linkifyText()` for descriptions), including attributes (`placeholder`, `title`, `style`). A headless XSS render test recipe exists (jsdom, hostile payloads via API, assert inert render) — rerun it when touching render functions.
- **Schema migrations:** sql.js has no `ADD COLUMN IF NOT EXISTS`. Use `ensureColumn(table, col, def)` in `db.js` (checks `PRAGMA table_info`) and add the column to `CREATE TABLE` too. Runs every boot.
- **Foreign key cascades:** `db.js` sets `PRAGMA foreign_keys = ON`. `db.export()` — called by `saveDb()` on every write — silently resets it, so `saveDb()` reapplies it after every export. If cascades stop working, check this first.
- **Killing a test server: `lsof -ti :PORT | xargs kill`, never `pkill -f` on an env var.** `DB_PATH=x PORT=y node server.js` puts neither in the command line, so the old server survives and silently serves **stale code and a stale DB**. Burned a full test cycle.
- **Test suites must fetch entity ids from their own setup responses, never hard-code them** — ids depend on how many suites ran before on the shared DB.
- **jsdom's `getComputedStyle` is unreliable through multi-class compound selectors** — it resolved `text-decoration` for `.task-item.completed.done-elsewhere .task-description` but returned the base color. Assert cascade-dependent styling **structurally** (rule text exists) and verify the look through WebKit.
- **Rendering a fetch-dependent page through qlmanage:** load it in jsdom against the live test server, wait, then serialize — copy each `textarea.value` into its `textContent` (and each `input.value` into its `value` attribute), strip `<script>`, write `document.documentElement.outerHTML`, qlmanage that.
  - **Strip every entry animation in the serialized copy, always.** qlmanage snapshots before an `animation: rise`/`slideDown` finishes, so cards that start at `opacity: 0` photograph as an empty page and read as a broken render (cost a debugging round on `/lists`, after the same trap on the briefing pane). `sed 's/animation: <name> …;/animation: none;/'` or append `.thing, .thing * { animation: none !important; opacity: 1 !important; }`.
  - **To photograph an absolutely-positioned board child** (the subtask pane, the briefing pane) **extract it instead of shooting the board.** jsdom has no layout, so the pane sits where nothing reserves room for it and the shot comes back blank. Pull `pane.outerHTML` plus the page's whole `<style>` into a scratch file, add `position: static; width: 200px`, and qlmanage that — it also puts the component at its REAL width, which is the question being asked.
- **Testing timezone without mocking the clock:** drive requests with `x-tz: Pacific/Kiritimati` (UTC+14) and `x-tz: Pacific/Niue` (UTC-11) — **25 hours apart, so their dates always differ**. Assert `due_today` counts a deadline in the zone where the day has arrived and an overdue task spills to the *caller's* today. Frontend: run jsdom under `TZ=America/Chicago` (`process.env.TZ` is what jsdom's `toLocaleDateString` reads).
- **The schema in `db.js` is one big SQL template literal — a backtick in a `--` comment ends it.** `node --check src/server.js` does not parse `db.js`; run `node --check src/db.js` after touching the schema (a comment quoting `` `day` `` stopped the server booting on 2026-09-23, caught by the headless test before push).
- **`node -e "require('./src/server.js')"` is not a syntax check** — it boots a server and grabs port 3000. Use `node --check src/server.js`.
- **Local API testing:** `DB_PATH=<tmp> PORT=<free> ANTHROPIC_API_KEY=dummy node src/server.js` and curl. Port 3000 is often taken. The frontend calls a relative `/api`.
- **Quick frontend syntax check:** extract the inline `<script>` and run it through `vm.Script` in Node.
- **jsdom computes styles but renders nothing, so it cannot tell you a control is invisible.** The focus toggle passed every structural assertion while unseeable. **For "can you see it / does it read at size", render through WebKit:** a scratch HTML with the element at real size beside real neighbours, `qlmanage -t -s 900 -o /tmp scratch.html`, look at the PNG.
- **Headless frontend E2E:** `JSDOM.fromURL` against a throwaway server with `runScripts: 'dangerously'`. jsdom has no `window.fetch` — bridge to Node's fetch resolving relative URLs; use a unique company name per run (subdomain UNIQUE).
  - **jsdom has no pointer, so `:hover` never matches.** Anything reading `document.querySelector('…:hover')` (`hoveredTaskRow()`) needs `document.querySelector` temporarily swapped. Restore immediately.
  - **An open inline-edit field kills every hover/keyboard gesture in the same test.** The digit branches early-return when focus is in an `INPUT`, so a headless run that renames something and then presses `3` silently does nothing and reads as a broken feature. Order the assertions so any test that opens a field comes last.
  - **The `:hover` stub must answer for both targets.** A row-hover stub must explicitly return `null` for `.task-arrow:hover`, or the arrow branch (checked first) swallows the digit.
  - **Top-level `let`/`const` in the page are NOT on `window`** — `w.tasks` is `undefined`. Function *declarations* are (`w.restoreSession()`, `w.getTodayKey()`). Re-fetch task state from the API.
  - **jsdom has no `Element.scrollIntoView`**; `selectDay()` calls it on a 0ms timeout, so clicking a day card prints a `TypeError` after assertions pass. Stub it (`w.HTMLElement.prototype.scrollIntoView = () => {}`).
  - **A task row's `textContent` starts with the circle and → arrow**, never the name. Find rows via `.task-description` and `.closest('.task-item')`.
- **Testing anything that calls Anthropic:** copy `src/` and `public/` to a scratch dir, symlink `node_modules`, replace `src/ai.js` with a stub exporting the same surface (`generateSubtasks`, `researchSubtasks`, `triageCosts`, `takeUsage`, `COST_MIN_CONFIDENCE`). The server picks it up because it only `require('./ai')` lazily. This is how the two-phase research path was verified free, and a stub with a deliberate delay is the only way to test what happens *while* research runs.
  - Keep the stub's fixture text stable across runs — four "failures" once were a stub that had renamed its tasks.
- **Testing a schema migration:** build a DB with current code, `ALTER TABLE … DROP COLUMN` the new column, boot against it — a genuine pre-migration DB, the only way to prove a backfill produces the order users *see*. Boot twice to prove one-shot.
  - To reach a signed-in board without the signup form: seed via fetch, set `localStorage['movealong.session'] = JSON.stringify({subdomain, slug, projectId})` (exact keys — `slug`, not `userSlug`), call `restoreSession()`, wait for render.
- **HTML5 drag & drop:** `dragstart` must call `e.dataTransfer.setData('text/plain', ...)` or Safari never initiates. `.task-item` has `user-select: none`, which drag needs.
- **Safari ignores `focus()` inside a `visibility: hidden` subtree.** Modals fade via `visibility` + `opacity`, so defer the focus (`setTimeout(() => input.focus(), 50)`).
- **Help-page vignettes (`help.html`):** looping pure-CSS mini-scenes in column 2 of the `three-col` grid, shared vocabulary (`.mini-card`/`.mini-task`/`.mini-circle`/`.mini-day`, real dates via `data-day-offset`, one storyline: a backyard fence). Section order: The board (Add · Move forward · **Lock a deadline** · Complete/postpone · Overflow · Projects) → **More fun** (Links, Prioritize, **Repeat**, **Goal for the day**, Create lists, **Dark mode**, **Focus on one day**) → Power moves → Subtasks → **Add calendar events (Beta)** → Run your own copy → Enabling real AI steps.
  - **A demo can claim column 3** (`.card.demo.demo-3`) when the card's point *is* a comparison (Projects' deadline-flagged tab bar, Dark mode's dark still). Under 760px it falls back to `grid-column: auto`.
  - **The two light/dark stills hard-code their own chrome colours**; each must keep its theme in *both* modes.
  - **Scene CSS declared above the `.nav-ring` block must compound its selectors** (`.nav-ring.spill-ring`, and its `ellipse` animation override); `.scissors-ring` only works bare because it's declared after. Cost two debugging rounds. The theme toggle sits **right** of "← Back to your board".
  - **Never stagger elements in an infinite loop with `animation-delay`** — it phase-shifts the element against the scene's fade. Give each its own `@keyframes` with percentage offsets on the same duration (`stepIn1..5`, `clock1..3`).
  - **Pin `opacity` (and any reset property) at every visible keyframe.** A property keyed only in the last frames interpolates from its implicit start across the ENTIRE cycle.
  - **Anchor animated cursors inside their click target** (`top:50%; left:50%`; the rest position is an offset in keyframes). Absolute scene coordinates misaligned twice.
